# R1. 바이브 코딩과 에이전트 코딩 도구의 개발 공수 절감 효과, 근거 조사와 역할별 배수

> **요약**
> 1. 2024~2026 통제 실험과 대규모 현장 연구 12건을 이 팀 조건(신규 개발 위주, 신규 입사자 다수, 도메인 특화 라이브러리, C3 반출 금지)에 맞춰 가중하면, 코딩 작업 시간은 **약 14% 줄어든다**(가중평균 시간배수 0.86). 리뷰, 보안, 재작업을 넣은 순효과로 보면 개발 공수 전체는 **1안(외부 API 코딩 + C3만 로컬) 기준 약 9% 감소**(보수 1%, 낙관 18%), **2안(로컬 LLM 단일)은 약 3% 감소**(보수 −3%, 낙관 12%)다. 모두 추정이다.
> 2. 역할 간 차이가 크다. **AI(신규 Python, MCP) 0.82**가 가장 크게 줄고, DATA, ML, AX 0.92, OPS 0.95, CAE 0.96, RUN 0.97, SIM 0.98, MBSE 0.99 순이다. PyAEDT 같은 도메인 라이브러리, C++ 물리모델, MBSE 는 보수값이 1.0을 넘는다(오히려 느려질 수 있음).
> 3. 현재 `method.json` 임시값(AI 0.70, RUN 0.80 등)은 근거에 비해 낙관적이다. 임시 기준값은 대체로 이 보고서의 **낙관(lo)** 수준이다.
> 4. AI 사용이 늘면 결함과 리뷰 부담도 늘어난다는 근거가 일관되게 나온다(Faros 2026: 개발자당 버그 +54%, 리뷰 시간 5배 / SusVibes: 기능 테스트를 통과한 에이전트 코드의 약 80%가 취약). 그래서 **검증 오버헤드(역할 공수의 3~6%)를 배수에 포함**했다. 릴리즈 후 운영(RUN)은 보수 시나리오에서 1.08로 오히려 늘어난다.
> 5. 도구 숙련 기간은 **3개월(2~4개월)**로 잡고, 그동안 효과를 절반으로 가정한다. 개발자 자기 보고는 과대평가된다(METR: 체감 +20%, 실측 −19%). 그래서 '27 Q1부터 WP별 계획 MM 대비 실측 MM, 재작업률, 결함으로 분기마다 보정한다.

- 조사일: **2026-10-21 (KST)** / 대상: LiDAR 개발 AX 우선 3과제(AL-1, VV-1, VV-3) '27 리소스 플랜. **조사만 했고, 만들거나 설치한 것은 없다.**
- **배수 정의**: 역할 공수 × 배수 = 바이브 코딩 적용 후 공수. 1.0은 변화 없음, 0.8은 20% 감소, 1.05는 5% 증가다. 리뷰, 검증, 보안 점검과 재작업까지 넣은 **순효과**다.
- **시나리오**: hi = 보수(효과가 작아 배수가 큼), base = 기준, lo = 낙관. `rates.json`, `method.json`의 표기와 같다.
- **환산**: 처리량 +X% → 시간배수 1/(1+X). 예: +26% → 0.79. 시간 −Y% → 1−Y.
- **신뢰도**: **상**(동료심사 논문과 1차 연구 원문) / **중**(공급사 보고서와 회사 보도자료와 발표 자료와 언론) / **하**(블로그와 포럼). "검색 요약"은 원문을 직접 열지 못하고 검색 결과 요약으로만 확인한 값이다. "공급사 마케팅"은 도구를 파는 쪽이 발표한 수치다.
- **추정**: 근거를 조합해 이 보고서가 계산한 값이다. **미확인**: 찾지 못한 값이다.

## 4. 역할별 배수 도출

### 4-1. 식 (추정)

**배수 m = 1 − s × g × (1 − c × (1 − L)) + o**

| 기호 | 뜻 | 값을 정한 방법 |
|---|---|---|
| s | 역할 공수 가운데 AI 코딩 도구가 닿는 개발 작업의 비중(코딩, 스크립팅, 디버깅, 문서). 나머지는 도메인 판정, 회의, 라이선스/연산 대기와 설치 | `model27.py` WP `basis` 문구로 역할 업무를 나눠 추정 |
| g | 그 작업의 시간 단축률 | 2-2 가중평균(0.14)을 기준으로 역할 적합도에 따라 조정. 최적 조건(greenfield Python) 0.20/0.35/0.50, 중간 0.10~0.15/0.22~0.28/0.35~0.42, 저적합(도메인 라이브러리와 물리 C++, MBSE) 0~0.05/0.15~0.20/0.30~0.35 |
| c | C3 맥락(도면, STP, BOM 원본)이 있어야 하는 작업의 비중. 그 몫은 로컬 LLM으로 처리 | 역할별 추정 |
| L | 로컬 LLM이 외부 최신 모델 대비 남기는 효과 비율 | 3장 SWE-bench Pro 격차(0.65~0.75)에 에이전트 반복 실패와 서빙 속도와 서버 공유를 감안해 hi 0.30 / base 0.50 / lo 0.65 |
| o | 검증과 보안 점검과 재작업 추가분(역할 공수 대비) | 1-4 품질과 보안 근거. 통제 실험은 본인 검토 시간까지 포함하므로, o는 **동료 리뷰와 보안 점검과 나중 재작업**만 |

- **보정 시점**:
  - 3월 말(ramp 중이므로 ×2 환산) → 6월 → 9월.
  - 실측이 hi보다 나쁘면 hi로 바꾸고 채용과 조달을 다시 본다.
  - 팀이 작아 통계 검정은 어렵다. 실측이 "hi~lo 범위 안에 있는지"로 판정한다.
- **하지 않을 것**: AI 허용과 금지를 과제 단위로 무작위 배정하는 실험(METR 방식). 표본이 너무 작고 R2처럼 선택 효과가 생긴다.

1. **정보보안 승인 범위**(`VIBE_SEC`): 사내 코드(C0~C2)를 외부 코딩 API로 보내도 되는지. 허용되지 않으면 1안 배수 대신 2안 참고값을 써야 한다.
2. **'26 EM 1차 구축 실적에 AI 코딩 도구를 썼는지**: "도메인 확장 표준" raw 추정에 이미 반영돼 있으면 배수가 이중으로 적용된다.
3. **2026년 기업 대상 에이전트 코딩 RCT(순공수 기준)**: 찾지 못했다. F1(Microsoft 2026)은 PR 수 기준 관측 연구다.
4. **PyAEDT, PyMechanical 공식 MCP**: Fluent, CFX만 확인했다. 서드파티 AEDT MCP는 비상업 라이선스다.
5. **최신 오픈 웨이트 모델(GLM-5.x, Qwen3.6+, DeepSeek V4, Kimi K2.6)의 같은 하네스 SWE-bench Pro 점수**, 그리고 8× RTX PRO 6000에서의 동시 코딩 세션 수와 토큰 속도.
6. **Claude Code 하네스에 로컬 모델을 붙였을 때의 도구 호출 신뢰도**와 공식 지원 범위.
7. **LG CNS, 서강대 연구**의 측정 지표(FP, MM 등)와 업종별 표본 수. 보도자료만 확인했다.
8. **Stanford(F2) 연구**의 동료심사판과 2026년 갱신 결과. 발표 자료만 확인했다.
9. **C++ 물리 시뮬레이션과 CAE 스크립팅과 MBSE 대상 통제 실험**: 없음. 그래서 CAE, SIM, MBSE 배수는 추정 비중이 크다.
10. **개발자 대상 "11주 숙련" 1차 출처**: 못 찾았다(M365 Copilot 설문 유래로 보여 쓰지 않음).

12. **CMU Cursor 연구(F3)**의 v3 최종 수치(경고 +30%, 복잡도 +41%는 v2 기준 검색 요약).
