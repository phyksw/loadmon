# LoadMonitor22 — 활동 흔적 기반 로드율 (PC 가동 하한 보정)

## 이 저장소 = 풀패키지

내장 파이썬 런타임(`python\`, CPython 3.11 embeddable 34파일 약 21MB)까지 함께 들어 있다 —
**clone 한 폴더에서 `LoadMonitor22-UI.bat` 을 더블클릭하면 그대로 실행된다**(PC 에 파이썬이 없어도 된다).
PC 에 파이썬이 있으면 그것을 써도 되고, `python\` 폴더를 지우면 `tools\Get-EmbeddedPython.ps1` 로 다시 받을 수 있다.

수집·분석 산출물(`data\` `report\` `teamdata\`)은 개인 자료라 저장소에 넣지 않는다.
`config\config.json` 은 배포 기본값이다 — 내려받은 뒤 `owner`·`watchFolders`·`teamServerUrl` 을 자기 환경에 맞게 고친다.

**결과가 어떻게 생겼는지 먼저 보려면** → [`samples\`](samples/README.md) — 가상 3인 팀으로 돌린
개인 분석 리포트 · 얼린 보고서 · 팀 통합 보고서 샘플(전부 합성 자료, 개인정보 없음).

## v22.0 — 보완툴 3종 본체 통합 · 시간 측정 검증 보완 · 일 상한 폐기

LM20 위에 따로 돌리던 **보완툴 / 보완2 / 팀보완툴 bat 을 없애고** 그 기능을 `LoadMonitor22-UI.bat`
하나에 넣었다. 동시에 로드율의 시간 측정 규칙을 재검증해 과대·과소 원인 16가지를 고쳤고,
"하루 최대 13h(코드상 16h)" 상한을 폐기해 **실제로 일한 시간이 그대로** 보이게 했다.

### 2. 시간 측정 검증 — 무엇이 과대·과소였고 어떻게 고쳤나

합성 자료 31가지 상황(회의만 있는 날, 반차, 야근, 주말, 일괄 복사, 샘플러 간격 변화 …)으로
LM20 의 규칙을 하나씩 재측정했다. 고친 것:

**과대 평가 원인**

- 참조(CC)·수신 메일 한 통에도 "PC 켜진 시간 전부" 하한이 발동했다 → 하한은 **능동 흔적**(산출물·발신·수락 회의·샘플러)이 있는 날에만(`pcFloorNeeds`).
- 하한 기준이 점심을 포함한 PC 켜짐이었다 → 12~13시에 흔적이 없으면 **점심 1h 차감**(`lunch`).
- 반차 날에도 전일 하한이 붙어 로드율이 2배가 됐다 → 반차는 **가용 비례**(최대 4h + 흔적).
- 수신 메일끼리 45분 간격으로 '다리'를 놓아 빈 시간을 채웠다 → 수동 신호는 다리를 놓지 않는다.
- 회의는 정확히 재는데 '회의' 신호가 다시 ±30분 세션을 만들어 회의마다 30분이 얹혔다 → 회의 신호 단독 폭 0.
- 미응답 초대(미정)도 참석으로 계상 → Outlook `ResponseStatus`(수락/거절/미응답) 수집, `tentativeMeetings` 설정.
- OneDrive 재동기화·폴더 복사로 같은 분에 몰린 파일이 야근·주말 근무가 됐다 → **같은 분 8건 이상은 시간 근거에서 제외**(`fileBurstN`, 가중치는 유지).
- PC 기록 오류(on 26h, night>on)·미래 시각 mtime 이 그대로 시간이 됐다 → 입력에서 물리 한계로 잘라 **이상치 장부**에 남긴다.

**과소 평가 원인**

- 창 샘플러 간격을 60초로 가정해 120초로 돌면 절반이 사라졌다 → 실제 간격을 추정해 인정.
- 3분 이상 손을 떼면(읽기·생각) 통째로 버렸다 → idle 5분(`idleActiveSec`) + 같은 창 제목은 10분까지 이어 붙임.
- 샘플러가 오후에만 돌면 오전 하한이 통째로 꺼졌다 → 샘플러가 덮은 시간만 대체하고 나머지는 하한 유지.
- 19시 이후 PC 가동은 어떤 경우에도 인정되지 않았다 → 산출물 ±30분 안의 **저녁·새벽 가동을 인정**(PC 야간 기록 합 이내, `eveningCredit`).
- 주말은 수락 회의도 버리고 산출물 ±30분만 → 산출물이 있는 창 안의 PC 가동을 인정(`weekendWindow`).
- HR 에만 있는 연차·명절이 가용에 남았다 → PC 도 흔적도 없는 평일은 **부재로 추정**해 가용에서 뺀다(`inferAbsence`).

**상한 폐기** — README 의 "일 상한 13h" 문구와 코드의 16h 상한(`DAY_SANITY_CAP`)을 모두 없앴다.
남는 것은 입력의 물리 한계(PC on≤24h·야간≤13h·주간≤11h, 회의 8h·자정 분할, 미래 시각 폐기)뿐이라
하루가 24h 를 넘을 수는 없고, 16h 초과일·부재일의 흔적·PC 기록 오류는 잘라내지 않고 근거 카드와
리포트 8절의 **이상치 표**에 날짜별로 보인다. 원하면 `config.mm.dayCapHours` 로만 상한을 건다(기본 없음).

**팀 비교 주의** — 측정 규칙이 바뀌었으므로 LM20 결과와 섞어 비교하지 말고 전원 LM22 로 다시
계산한다(같은 자료에서 하한 모드는 점심 차감으로 약 −10pt, 야근·주말이 많은 사람은 +).

새 설정 키(`config.mm`, 전부 기본값 있음): `pcFloorNeeds` `lunch` `dayWindow` `tentativeMeetings`
`eveningCredit` `weekendWindow` `inferAbsence` `idleActiveSec` `fileBurstN` `spanFromAllFiles`
`mailTimeOffsetH` `dayCapHours` — 설명은 `config\config.default.json` 의 `_mm_옵션_설명` 과 docs\설정가이드.

`config.copilotAuto` 에도 세 키가 생겼다(전부 기본값 있음): `judgeChunk`(40) `refineChunk`(20) — 한 왕복에
넣는 신호·행 수, `sendSenderAddress`(false — 프롬프트에 메일 상대의 주소 대신 도메인만). 설명은
`_copilotAuto_옵션_설명` 과 docs\설정가이드 §8-1(Copilot 이 채우는 캐시 파일은 §8-2).

파일을 고쳤으면 **`python tools\update_files.py`** 로 `FILES.txt` 를 다시 만든다 — `tools\Make-Package.ps1`
이 FILES.txt 의 크기·crc32 를 실제 파일과 대조해 낡은 목록이면 담지 않고 멈춘다(`--check` 는 대조만).

## v20.1 — "팀 서버가 아닌 다른 프로그램이 쓰고 있습니다" 의 정체와 [포트 가져오기]

실사용 제보: 팀 서버를 켜려니 *"포트 9310 을 팀 서버가 아닌 다른 프로그램이 쓰고 있습니다"* 가
뜨고 손쓸 방법이 없었다.

**정체는 남의 프로그램이 아니라 우리 자신의 구버전이었다.** LM18·LM19 의 팀 서버에는
v20.0 에서 새로 만든 신원 응답(`/api/whoami`)이 없다. 그래서 예전 폴더에서 켜 둔 팀 서버가
9310 을 쥐고 있으면, 새 대시보드가 그것을 "LoadMonitor 가 아니다" 라고 판정했다.
재현해서 사용자가 본 문구를 글자 단위로 확인했다.

### 무엇이 쥐고 있는지 이름으로 말한다

포트 상태를 여섯 갈래로 가른다 — **내 폴더의 서버 / 다른 폴더의 팀 서버 / 예전 버전 팀 서버 /
LoadMonitor 가 아닌 프로그램 / 확인 못 한 프로그램 / 붙잡은 서버가 없는데 막힘.**
어느 경우든 화면이 **프로세스 이름·PID·실행 파일·명령줄·실행 계정**을 그대로 보여 준다.

### [포트 가져오기] — 원하면 강제로 넘겨받는다

사용자가 요청한 기능이다. 다만 포트 하나 때문에 PC 를 망가뜨릴 수는 없으므로 선을 그었다:

- **죽일 대상은 OS 사실로만 정한다.** 신원 응답(JSON)은 그 포트에 먼저 붙은 아무 프로그램이나
  흉내낼 수 있다(반박 검증에서 실제로 재현했다). 그래서 종료 판단은 명령줄·소유 계정·이름으로만 한다.
- **`/T`(자식까지) 종료를 쓰지 않는다.** 대상을 잘못 집었을 때 트리 종료는 보험이 아니라 피해 확대다.
- **정체가 확인되지 않은 프로그램에는 정상 종료 요청조차 보내지 않는다** — 그쪽의 다른 기능일 수 있다.
- **LoadMonitor 팀 서버가 아니면 PID 를 직접 입력**해야 진행된다. 반사적 클릭을 막는다.
- 시스템 프로세스, 다른 계정 소유(명령줄을 읽을 수 없는 것), 대시보드 자신과 그 부모는
  **어떤 경우에도 종료하지 않는다.**
- **켠 뒤에 "지금 답하는 서버가 방금 내가 띄운 그놈인가" 를 확인한다.** 윈도우는 살아 있는 리스너
  위에 덧바인딩을 허용해서(SO_REUSEADDR), 아무도 죽이지 않았는데 "가동 성공" 이라 말하고 업로드는
  계속 남의 서버로 가는 상태가 만들어질 수 있다(실측). 확인에 실패하면 방금 띄운 것을 스스로
  정리하고 실패로 보고한다.
- 무엇을 죽였는지 진행 로그에 남긴다.

### [포트 바꾸기] — 죽이지 않는 길

권하는 쪽이다. 새 번호를 받아 `config.teamServerUrl` 을 원자적으로 고치고, **팀원들이 쓰는 주소가
바뀐다**는 사실과 방화벽 허용이 다시 필요하다는 점을 함께 알린다. 예약 포트 범위·대시보드 자신의
대역·이미 쓰이는 번호는 미리 거른다.

> **이 PC 에서 확인된 함정 하나:** TCP 임시 포트 범위가 `1024~15000` 이었다(윈도우 기본값
> 49152~65535 가 아니다). 9310 이 그 안에 들어, 아무 프로그램이 바깥으로 연결할 때 그 번호를
> 잠깐 배정받아 서버가 못 뜰 수 있다. 이때 주인은 LISTEN 이 아니라 나가는 연결이라 강제 종료
> 대상이 아니다 — 화면이 그 사실을 말하고 `19310` 처럼 범위 밖 번호를 권한다.

### 그 밖에 함께 고친 것

- `netstat -ano -p TCP` 는 **IPv6 리스너를 통째로 못 본다**(실측: IPv6 행 0/166) → `-p` 를 빼고
  직접 거른다. 한 포트에 리스너가 둘일 수 있으므로 **전부** 찾아 다룬다.
- "알아내지 못했다" 와 "아무도 안 쓴다" 를 구분한다. 예전에는 둘 다 0 이라 강제 종료가 조용히
  아무것도 하지 않았다.
- 다른 계정이 띄운 프로세스는 명령줄이 비어 온다 → "팀 서버가 아니다" 로 단정하지 않고
  "확인 불가" 로 다뤄, 진짜 우리 서버를 못 끄던 경로를 없앴다.
- 서버가 켜질 때 `report\teamserver.token` 에 난수를 남기고 신원 응답에 되비춘다 —
  그 파일을 읽을 수 있다는 것이 "같은 계정·같은 폴더" 의 증거다.
- 팀 서버가 포트를 열지 못하면 **WinError 를 그대로 로그에 적는다**(10013·10048 은 조치가 다르다).
  예전에는 traceback 만 남고 화면에는 "시작 실패" 만 떴다.
- 중지도 같은 규율로 — `report\teamserver.pid` 를 그대로 믿지 않고 지금 그 포트를 쥔 프로세스를
  다시 확인한 뒤에만 종료한다(창을 X 로 닫으면 pid 기록이 낡은 채 남는다).
- "팀원에게 알려줄 주소" 는 **이 PC 안에서 확인된 것**이라고 명시한다 — 방화벽 인바운드가 막혀
  있으면 팀원은 못 닿는다.


## v20.0 — 실측 제보 대응: 팀 서버 신원 · 화면 그대로의 리포트 · PC 이동

회사 PC 에서 실제로 써 보며 나온 제보 셋을 재현해 원인까지 확인하고 고쳤다.

### 1. 팀 업로드가 엉뚱한 곳으로 가고, 종료가 안 되고, 대시보드가 비던 것

증상은 셋이었지만 **뿌리는 하나**였다 — 팀 서버에 신원이 없었다. 서버는 포트로만 불렸는데
저장 위치는 그 서버가 실행된 **폴더**로 정해졌다. 그래서 이름이 다른 설치본(LoadMonitor19,
예전 복사본, 이름 바꾼 폴더)이 먼저 포트를 잡고 있으면:

- 대시보드는 포트가 열려 있다는 것만 보고 "이미 켜져 있습니다" 라고 답했고 → **업로드가 그 남의
  폴더 teamdata 로 들어갔다**
- 그 경로에서는 pid 기록을 남기지 않으니 → **[팀 서버 중지] 가 아무것도 죽이지 않았다**
- 이 폴더의 teamdata 는 생기지도 않으니 → **팀 대시보드가 빈 채로 보였다**

고친 것:

- **서버가 자기 신원을 말한다** — `/api/whoami` 로 자기 설치 폴더·저장 위치·pid·포트를 알린다.
  대시보드는 포트가 아니라 **신원**으로 '내 서버'를 판단한다.
- **남의 서버면 솔직히 거절한다** — "포트 9310 은 다른 폴더의 팀 서버가 쓰고 있습니다: `<그 폴더>` /
  저장 위치: `<그 폴더>\teamdata` / 지금 업로드하면 그 폴더로 들어갑니다". 남의 서버는 죽이지 않는다.
- **누가 띄웠든 중지된다** — pid 파일은 이제 서버 자신이 쓴다(bat·대시보드·손수 실행 모두).
  중지는 3단계다: ① 정상 종료 요청(`/api/shutdown`, 로컬 전용) → ② 검증된 pid → ③ 포트 주인 추적.
  ②③ 은 "정말 teamserver 인가"를 확인한 뒤에만 종료하므로, **재사용된 옛 pid 로 애먼 프로그램을
  죽이던 위험**도 함께 사라졌다.
- **받는 곳과 보는 곳을 하나로** — 팀 서버도 `teamShareDir` 를 우선 쓴다(예전엔 teamdata 고정이라,
  공유폴더를 설정한 PC 에서 서버를 켜면 받은 자료가 그 화면에 영영 안 떴다).
- **업로드 결과가 자리를 말한다** — "4개 파일 저장 · 저장 위치: `<경로>`", 같은 PC 의 다른 폴더가
  받았으면 `[!] 이 PC 의 다른 폴더가 받았습니다`.
- **bat 의 포트 하드코딩 제거** — `config.teamServerUrl` 하나로 통일(bat 과 화면이 어긋날 수 없다).

### 2. 팀 대시보드가 '초기화' 되거나 다른 경로를 보던 것

`team_share()` 가 요청마다 파일시스템을 찔러 보고 답을 **다시 정했다**. 설정한 공유폴더가 잠깐
안 잡히면(네트워크 끊김·오타) 말없이 이 PC 의 teamdata 로 갈아탔고, 한 번의 새로고침 안에서도
두 요청이 서로 다른 폴더를 볼 수 있었다 — 명단이 통째로 바뀌는 그 '초기화'다.

이제 **자리는 사람이 정한 곳에 고정**된다. 못 읽으면 갈아타는 대신 그 사실을 화면에 적고,
`[이 PC 의 teamdata 로 전환 (N명)]` 버튼을 준다. 받는 곳과 보는 곳이 다르면 빨간 경고로 알린다.
설정 저장도 임시파일 → 교체(원자적)로 바꿔, 쓰다 만 config 가 '설정이 통째로 없음'으로 읽히지 않는다.

### 3. 유사 항목 정리가 '성공' 이라 말하고 안 합쳐지던 것

Copilot 의 답을 **그대로 저장하고 그대로 적용**한 것이 문제였다. 띄어쓰기 한 칸, 대소문자 하나만
달라도 매칭이 실패했고, A→B·B→C 사슬은 풀지 않아 화면에 두 줄로 남았으며, 못 붙인 이름은 조용히
버리고 '몇 개 그룹 통합'만 세어 성공이라 보고했다.

- **이름 축을 정규화**한다(연속 공백·앞뒤 공백·대소문자) — 읽을 때도 적용하므로 **이미 공유폴더에
  저장된 옛 `team_aliases.json` 도 다시 돌리지 않고 살아난다**.
- **사슬을 끝까지 따라간다**(순환이 와도 한 이름으로 모은다).
- **버린 이름을 보고한다** — "목록에 없는 이름 2개는 건너뜀", 하나도 못 붙였으면 그 이유를 화면에.
- 프롬프트를 **한 줄에 한 항목**으로 바꿔, 모델이 이름을 다시 타이핑하지 않고 그대로 옮기게 했다.
- 함께 확인된 결함 하나 더: **원본보다 오래된 정제본(`_refined`)이 새 결과를 이겼다**(정제 없이

## v18.3 — 자동 실행 사슬 강화 (Agentic 매칭 · 워크플로우)

"분석 실행 뒤 Agentic 매칭·워크플로우가 자동으로 안 돈다"는 제보(2회)에 대응.
코드 사슬(판정→정제→Agentic→워크플로우)은 그대로였고, 실제로는 뒤 단계가 Copilot 일시
거부로 **실패**하거나 **실행 조건(AI 정제 체크·판정 성공)** 을 못 채운 것을 화면이 말하지
않아 '자동 실행이 꺼진 것'처럼 보였다.

- **뒤 단계 1회 재시도** — Agentic 매칭·워크플로우가 실패하면 15초 뒤 한 번 더 시도한다
  (긴 판정 뒤 Copilot 이 일시적으로 응답을 거부하는 실측 패턴). 재시도 사실은 기록에 남는다.
- **탭이 이유를 말한다** — Agentic AI·담당자 워크플로우 탭이 비어 있으면 최근 실행 기록을
  함께 보여준다: "최근 실행에서 실패: <사유>" / "AI 판정 단계에 도달하지 못했습니다" /
  "이 단계 기록이 없습니다(AI 정제를 끄고 실행했을 수 있음)". 침묵하는 빈 화면은 없다.
- **자동 사슬 회귀 시험** — 스텁으로 [분석 실행](AI) 한 번에 네 단계가 전부 돌고 산출물이
  생기는지, 1회 실패 뒤 재시도로 살아나는지, 탭 사유 표시까지 15시험(기존 커버리지 공백이던
  워크플로우 단계 포함).

자동 실행 조건(변함없음): [분석 실행] 시 **AI 정제 체크**가 켜져 있고 AI 판정이 성공해야
뒤 단계가 이어진다. 체크를 끄면 규칙 결과만 만든다.

## v15.1 — AI 정제 복구 (근거가 사라지고 있었다)

사용자 지적("LM9~11 은 라벨링이 잘 됐는데 지금은 raw 느낌", "여전히 정제에 실패",

**① 정제 프롬프트에 원문 근거가 0바이트로 나가고 있었다** (가장 큰 원인)
- `mine.py` 는 `evidence_*.md` 를 **규칙 이름**(`글쓰기`·`agentic`·`미지정`)으로 쓴다.
  그 뒤 `judge.py` 가 `mm_rows` 의 Level 2 만 **판정 이름**으로 덮어쓰고 근거 파일은
  재생성하지 않는다. `refine.py` 는 판정 이름으로 근거를 찾으니 **매칭이 항상 0건**이다.
- 실측: 근거 파일 2,131자 중 프롬프트에 실린 것 **0자**. 두 회차 모두 `[항목별 원문 근거]`
  블록이 아예 없었다. AI 는 "원문의 고유명사를 살려 쓰라"는 지시를 **원문 없이** 받았다.
- 구버전(LM9~11)은 매칭 실패 시 근거 파일 앞 4,000자를 보내 이 불일치를 덮고 있었다.
  LM13 이 그 폴백을 **대안 없이** 없애면서 결함이 드러났다.
- 수정: 근거 원천을 `signals_{tag}.csv` 로 바꿨다. 이 파일은 judge 가 판정 축으로
  재작성하므로 `model`=Level 2, `detail`=Level 3 으로 **키가 정확히 일치**한다.
  항목마다 자기 근거만 붙이고 `## #항목번호` 앵커로 묶는다. 구버전 폴백은 되살리지
  않았다 — 청크가 2개 이상이면 뒤 청크가 남의 과제 근거를 받기 때문이다.

  처럼 실제 산출물을 짚는다.

**② 근거가 없을 때 프롬프트가 거짓말을 하고 있었다**
- 근거를 0바이트로 보내면서 "각 항목의 실제 원문 근거입니다"라고 선언했다. 창작을 부르는

- 수정: 근거 상태(정렬됨/부분/없음)에 따라 선언과 5번 규칙을 바꾼다. 근거가 없으면

**③ 내장 파이썬 PC 에서는 AI 정제만 단독으로 죽었다**

## v15 — LM11 기반 + LM14 기능 이식 (분류 성능 회복)

LM13·LM14 에서 과제명이 `core`·`target`·`txt` 같은 **파일명 조각**으로 흩어지던 문제가
반복돼, **분류기는 LM11 것을 그대로 쓰고** 그 위에 뒤 버전의 확정 수정만 이식했다.

**분류 (LM11 유지 + 근거 보강)**
- **폴더 근거** — 파일 신호에 `| 폴더:<프로젝트 폴더>` 를 붙인다. 사람은 프로젝트를 폴더로
  나눠 쓰므로 파일명 조각보다 훨씬 안정적인 단서다. 지정 과제 매칭·AI 판정·토큰 추출이
  모두 이 폴더를 보게 된다. `src`·`build`·`temp` 류 구획 폴더는 건너뛰고 위로 올라간다.
- **별칭 귀속** — 지정을 `(과제명, [매칭어])` 로 다룬다. 예전엔 매칭어가 그대로 과제명으로
  올라와 `coding`·`target` 이 과제처럼 보였다. 이제 별칭에 걸려도 **상위 과제명으로 묶인다**.
- **토큰 경계 매칭** — `AX`⊂`tax`/`max`, `ai`⊂`email` 오귀속 차단.
- **판정 결과 재사용** — 한 번이라도 AI 판정에 성공하면 그 과제 체계를 다음 실행의 시드로
  쓴다. 이후 판정이 실패해도 화면은 과제명으로 묶인 채 유지된다. 판정 실패가 남긴
  규칙 폴백 산출물은 시드로 쓰지 않는다(토큰 고착 방지).

**Outlook 버전 강건성 (실측 대응)**
- 구형 Outlook 이 COM 서버로 등록돼 있고 그 설치본에 프로필이 없으면 **"Outlook 시작"
  설정 마법사**가 뜬다. 이때 `New-Object -ComObject` 는 **응답 없이 무한 대기**한다
  (실측: 300초 무응답 → 그 PC 의 메일·일정이 통째로 빔).
- 대응: ① 프로필이 없으면 COM 을 아예 부르지 않는다 ② Outlook 이 실행 중인데 붙을 수
  없으면(= 대화상자에 막힌 상태) `New-Object` 를 부르지 않고 **열려 있는 창 이름을 짚어**
  안내한다 ③ 바쁨(RPC_E_CALL_REJECTED)을 '설치 안 됨'으로 오진하던 분기를 고쳤다 —
  멀쩡한 PC 에 재설치를 권하던 경로다. 7분 대기 → **4.6초 안내**.
- 붙은 Outlook 의 **버전·실행 경로를 로그에 남긴다** — 'PC 마다 누락'을 원격으로
  판별하는 단서다.

**팀즈 · Copilot 분리**
- 팀즈 채팅은 Copilot 으로 조회되지 않는다(테넌트에 커넥터가 없으면 "조회 불가").
  기본값을 `teamsViaCopilot: false` 로 두고, 팀즈는 **상시 샘플러**나 Graph 로 모은다.
  Copilot 왕복은 AI 판정에 아껴 둔다 — 예전엔 팀즈 재시도가 판정 예산을 먹어치웠다.

**진단 (왜 결과가 이런지 보이게)**
- `report\last_run.json` 에 단계별 성공·소요·사유를 **단계마다 즉시** 기록한다. 중간에
  끊겨도 어디까지 갔는지 남는다.
- 대시보드가 원인을 특정해 띄운다 — 기간 불일치 / AI 미사용 / **판정 전 중단** /
  판정 실패 중 무엇인지, 그리고 가장 오래 걸린 단계.
- **[AI 연결 진단]** 버튼 — Copilot 왕복 1회를 실제로 돌려 어느 지점에서 막히는지 본다.

**시간 계상 정확도**
- 세션 병합 단조성 — 신호를 더 넣을수록 투입시간이 줄던 과소계상 제거.
- 자정을 넘는 회의 분할, 미수락 교육 제외(신호 필터와 동일 판정).
- 개인정보 필터가 **경로 전용 토큰**(`temp`·`다운로드`)으로 제목을 지우지 않는다.
  ASCII 는 단어 경계를 요구한다(`temp`⊄`template`). 무엇이 걸렸는지 기록에 남긴다.
- 비업무 키워드는 기본 목록과 config 의 **합집합** — config 지정이 기본 방어를 지우지 않는다.

**요청↔산출 페어링**
- 오더→산출 페어에 **내용 연관(공통 단어) 또는 같은 세부업무**를 요구한다. 예전엔 같은
  과제의 '다음 산출물'을 무조건 짝지어 무관한 파일 저장이 응답으로 잡혔다(미스매칭 다수).

**파이썬 없는 PC**
- `tools\Get-EmbeddedPython.ps1` 로 내장 파이썬을 받아 `python\` 에 두면 bat 이 자동으로
  그것을 쓴다. 설치 권한이 없어도 동작한다.

**검증** — 상속 회귀 6종 + LM18 전용 6종, 총 **180개 시험 통과**. 린트 5관문(ruff ·
PowerShell 파서 · 페이지 문자열 · bat 인코딩 · ps1 인코딩) 통과.

## v8 변경 — MM 산식 재정의

로드율이 높은지 낮은지 **한눈에 비교되도록** 두 숫자를 나란히 낸다.

```
1 MM      = 8h × 그 달 평일수            (주40시간 기준)
가용 MM   = (평일수 − 부재일수) ÷ 평일수   ← 연차·휴가는 '일자에서' 뺀다
투입 MM   = 실제 투입시간 ÷ (8h × 평일수)  ← 상한 없음. 야근하면 1.0을 넘는다
로드율(%) = 투입 MM ÷ 가용 MM × 100       ← 100% = 가용 시간을 꽉 채워 일함
```

- **연차는 일자에서 차감** — 5일 연차를 쓰면 가용이 (23−5)/23 = 0.78 MM 이 되고,
  그 기간 정상 근무했다면 로드율은 그대로 **100%** 다. 연차를 썼다고 로드율이 깎이지 않는다.
- **상한 없이 실측 그대로** — 주 52시간을 넘겨 일했으면 넘긴 만큼 반영된다. 잘라내지 않는다.
  야근한 달의 로드율은 100%를 넘는다(예: 125%).
- **야간은 'PC 켜진 시간'이 아니라 '산출물이 찍힌 시각의 폭'으로 잰다** — 20:00 커밋,
  23:30 파일 저장이면 3.5h + 여유 0.5h = 4h. 취침 중 켜둔 PC는 계상되지 않으면서
  진짜 야근은 정직하게 잡힌다.
- **평일 기준선 8h** — PC 가동시간을 근무시간으로 쓰면 회의·현장·외근·타 기기 작업이 전부
  0h가 되어 MM이 실제의 1/5로 붕괴한다(v7 이전 실측 3개월 0.45 MM). PC 기록은 ① 그날
  일했는지 교차확인 ② 정규시간 초과분 산정에만 쓴다.
- **연휴·장기부재 자동 감지** — 흔적이 전혀 없는 평일이 연속 3일 이상이면 투입에서 뺀다
  (음력 명절을 config에 안 넣어도 과대계상되지 않는다). 몇 회 제외했는지 UI에 표시된다.
- **의미 없는 일정 차단** — 취소 회의(`Canceled:`/`Cancelled:`/`취소됨`, 대소문자 무시),
  종일 일정(근태·행사 블록), '한가함(Free)' 상태 일정은 계상하지 않는다.
- 팀 총괄 리포트(aggregate.py)에도 인별 **투입/가용/로드율 + 신뢰도 근거**(무흔적 평일,
  연속공백 제외 횟수, 부재일, 신호 수)가 실린다.

## MM 산식

```
day_work = ∪(회의 구간, 창 샘플러 활동(≤60분 공백 잇기), 신호 세션, 저녁·새벽 크레딧)   [상한 없음 · 하루 24h 물리 한계만]
           · 능동 흔적(산출물·발신·수락 회의·샘플러)이 있는 평일: PC 가동 구간(pc_spans ∩ 08~19, ≤11h) − 점심·저녁(흔적 없는 만큼) 을 구간째 합침
             PC 기록 없는 날은 능동 흔적·회의 창 ±30분(pcFloorFallback) · 항상 켜진 PC 는 능동 흔적 ±30분까지 · 시차 근무 창 밖 ≤1h(flexEdgeH)
           · 종일 출장·현장·교육 일정(offsiteAsWork)·수동 기록(data\manual\worklog.csv): 표준일·기록 시간을 하한으로
           · 주말·공휴일: 산출물 ±30분 창 안의 PC 가동만(weekendWindow "pc" 는 가동 구간 전체) · 연차일: 흔적만큼 그대로(자르지 않음)
           · 수동 흔적(수신·CC·열람)만 있는 날: 하루 ≤60분, 하한 미적용 · 미래 시각·일괄 생성 파일(분당 1건 외)은 시간 근거 아님
MM(월)   = Σ day_work / (8h × 그 달 평일수)      가용 = (평일수 − 부재 − 추정 부재 − 오늘 잔여·미래 평일) ÷ 평일수
행 배분  = 신호 가중치 비중 × 총 MM              (비업무 판정으로 뺀 신호의 시간은 총 MM 에서도 뺀다)
```

3개월에 매일 8h를 다 채우면 3.0 MM. 입력의 물리 한계(PC on≤24시간·night≤13시간·주간≤11시간, 미래 시각·역행
회의 폐기)로 하루가 24h 를 넘을 수 없고, 이상치(PC 기록 오류·부재일 흔적·16h 초과)는 잘라내지 않고 근거
카드·리포트 8절에 표시한다. PC 도 흔적도 없는 평일은 부재로 추정해 가용에서 뺀다(config.mm.inferAbsence).
공휴일은 양력 고정일·근로자의날·연도별 표(설·추석·대체공휴일·선거일)가 내장돼 있다. 그날이 어느 방식(샘플러
실측·PC 하한·흔적 창·종일 행사·수동 기록)으로 계산됐는지와 커버리지 등급은 `mm_meta` 의 `measure`·`coverage` 에
남아 팀 취합에 배지로 보인다. 세부 옵션은 docs\설정가이드 §9.

## 사용

```bash
python run.py --from 2026-05-19 --to 2026-08-17            # 수집 + 추출
python run.py --from 2026-05-19 --to 2026-08-17 --ai       # AI 판정(계층)+내러티브+정제
python run.py --from ... --to ... --skip-collect --ai      # 재분석만
python aggregate.py \\서버\팀공유\LoadMonitor               # (팀장) 팀 총괄 리포트
```

또는 `LoadMonitor22-UI.bat` 더블클릭 → 브라우저 대시보드에서 [분석 실행].

**Python 3.11 이상**이 필요하다(`datetime.UTC`·`zip(strict=True)` 를 쓰므로 3.9·3.10 은 AI 판정·Teams(Graph) 수집에서 오류) — 파이썬이 없거나 낮은 PC 는 `tools\Make-Package.ps1 -Full` 풀패키지(내장 파이썬 3.11 동봉)를 쓴다.

첫 실행 전 `config\config.json`에서 반드시:

- **`watchFolders`** — 실제 산출물 폴더. 비면 설계·SW개발이 안 잡힌다.
- **`excludePathKeywords`** — 개인 폴더 키워드 (개인정보 마지막 방어선).
- **`projects`** — (선택) 과제명을 입력하면 AI 체계 수립에 힌트로 참고.
  비워둬도 상위개체 자동 발견이 작동하므로 타팀 배포 시 그대로 둬도 된다.
- (팀 배포 시) **`teamShareDir`** — 팀 공유폴더 경로.

## 산출물 (`report\`)

- `mm_rows_<기간>.csv` — 업무 행 (유형·과제·세부업무·MM·근거·확신도)
- `signals_<기간>.csv` — 신호별 원문·AI 판정 (raw 단서 — 오해석 방지의 근거)
- `pivots_<기간>.json` — 과제↔유형 양방향 피벗 + 공통업무 + 에피소드
- `ai_narratives_<기간>.json` — 월별 AI 리뷰 서술
- `entities_<기간>.json` — AI가 설계한 엔티티 체계
- `mm_rows_<기간>_refined.csv` — Level1·상세설명까지 붙은 최종 행

## 구성

```
run.py        통합 실행기 (수집 → mine → judge → refine → export)
mine.py       추출: 신호 → 가중치 → MM v3(근무일) 기준선
judge.py      AI 판정: 체계 수립 → 신호 계층 판정 → 피벗·에피소드 → 월별 내러티브
refine.py     AI 정제: Level1·상세설명 문장화
export.py     팀 공유폴더 내보내기  /  aggregate.py  팀 총괄 리포트(팀장용)
core/         extract.py(추출·MM 엔진) · board.py(배분표 엔진)
collect/      수집기 — PC가동(pc_on+pc_spans)·Outlook(COM→색인→웹→Copilot)·파일·Recent·git·팀즈(Graph→Copilot→창 3단 폴백)
              Register-Samplers.ps1(창·팀즈 샘플러 로그온 등록) · Add-WorkLog.ps1(PC 밖 업무 수동 기록)
tools/        copilot_auto.py(무개입 Copilot 왕복, GPT-5.6 자동 선택) · lint.ps1
ui/           대시보드 + 주간/월간/상세 리뷰 (포트 9148+)
```

## 다른 PC로 복사

폴더 통째로 복사하되 **data\ 와 report\ 는 제외**(개인정보). 복사 후 `python 자가점검.py`
로 누락 확인. 필수 목록·체크섬은 FILES.txt(고친 뒤에는 `python tools\update_files.py` 로 재생성).

## Copilot 무개입 연동

`tools\copilot_auto.py`가 전용 Edge 프로필로 M365 Copilot과 자동 왕복한다.
**최초 1회만** 열린 창에서 회사 계정 로그인이 필요하고, 이후는 사람 개입이 없다.
모델은 전송 전 GPT-5.6을 자동 선택(없으면 기본 모델로 진행하고 로그에 남김).
응답은 15초간 변화가 없을 때 완료로 판정한다(`config.copilotAuto.stablePolls × pollSec`).
