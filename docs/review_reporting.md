# LM25 보고·팀 집계 설계 검토

검토일: 2026-09-09. 담당 범위는 `aggregate.py`, `team_report.py`, `team_refine.py`, `export.py`, `teamup.py`, `report_out.py`, `freeze.py`, `core/board.py`, `core/owner.py`, `ui/app.py`의 개인·팀 표시 및 조정 흐름이다. 실행 진입점·수집·AI 자체 판정·팀 서버 수신 처리는 별도 담당 범위다.

**판정: 업무 투입과 자동화 후보를 탐색하는 기능 구성은 목적에 맞지만, 현재 팀 수치를 의사결정 근거로 확정하는 설계는 부족하다.** 특히 기간·분석 실행·사람 식별·비교 대상·자동화 MM의 의미를 하나의 계약으로 고정해야 한다. 린트의 성공으로 이 문제들이 검증되지는 않는다.

실제 개인 설정·data/report/teamdata는 읽지 않았다. 앱·서버·수집·AI·브라우저·업로드도 실행하지 않았다. 원본 함수와 상수·클래스를 AST로 분리하고 TEMP의 합성 파일만 사용했다. 결과는 [review_reporting_evidence.json](review_reporting_evidence.json)에 있다. 일부 계산은 원문 함수 직접 호출, 일부는 호출 경로의 정적 확인이다. HTML 화면을 브라우저로 확인한 결과는 아니다.

### R2 · P1 · 확정 — 관련 업무량을 절감 가능량처럼 제시하고 출력별로 다른 MM을 쓴다

- `team_report.py:662`–`669`의 AX 비율은 `(상 단계수 + 중 단계수×0.5) / 전체 단계수`다. `:977`은 업무 전체 MM에 이를 곱하고 `:2864`–`2866`은 'AX 가능 MM' KPI로 노출한다. 단계 소요시간·발생횟수·실증 절감률 입력은 없다.
- 재현: 동일 10 MM 업무를 상/하 2단계로 표현하면 5 MM, 상 단계 문구를 3개로 나누어 상/상/상/하로 표현하면 7.5 MM이 된다. 업무량·자동화 효과가 바뀌지 않아도 설명의 세분화로 50% 증가한다.
- `aggregate.py:624`, `ui/app.py:2086`·`:3514`, `report_out.py:311`은 `load_mm`을 사용하지만 통합 보고서는 `team_report.py:2956`의 `load_mm_split`을 우선한다. `freeze.py:688`–`691`은 둘을 병기하지만 `:810` 제목은 '대체 로드 MM'이다. 이전 계획 P1-3이 여전히 유효하다.
- 표현도 `report_out.py:192`–`194`의 '실측 그대로', `ui/app.py:3286`의 '판정 실측치'가 총시간 추정과 과제 배분의 한계를 흐린다. 적합률은 AI 판정이고 관련 MM은 코드 계산인데 `aggregate.py:612`는 모두 Copilot 판정치로 설명한다.
- 완료 기준: `estimated_work_mm`, `related_work_mm`, `unique_related_work_mm`, `allocated_candidate_mm`, `expected_saved_mm`을 구분해 공통 산출물에서 모든 출력이 동일 필드를 사용한다. 예상 절감은 검토된 단계별 시간×빈도×절감률 근거가 있을 때만 계산하고, 근거가 없으면 비어 있어야 한다. 단계 이름 분할로 효과가 바뀌지 않아야 한다. 후보 간 중복 제거 총량은 해당 관련 업무량을 초과하면 안 된다.

### R3 · P1 · 확정 — 비교 제외·설정 차이·0과 결측의 처리 기준이 출력마다 다르다

- `aggregate.py:177`, `:269`, `:533`은 정확히 unreliable일 때만 비교 제외한다. coverage가 없거나 등급이 잘못된 입력은 비교에 포함된다. `cfg_mismatch`는 과반이 없으면 아무 표시도 하지 않고(`:203`–`220`), 차이가 표시돼도 비교를 막지 않는다.
- 통합 보고서 `team_report.py:2386`–`2402`는 unreliable을 팀 투입에서 제외하면서 Agentic·워크플로우·AX MM 집계에는 포함한다. 따라서 같은 화면의 팀 투입과 자동화 KPI는 모집단이 다르다. 팀 UI `collect_team_data`는 unreliable의 Agentic도 제외하므로 두 출력의 범위가 다르다(`aggregate.py:533`·`:554`).
- `aggregate.py:76`은 공식 총량 0을 결측처럼 취급한다. 재현: `mm_scale(0, 2)`가 1을 반환하므로 공식 0 MM인데 행은 2 MM 그대로 남을 수 있다. 신뢰도 누락 입력은 `is_unreliable=False`; 표준시간 8h/6h의 2명은 설정 차이 목록이 빈 집합이었다.
- 완료 기준: 비교 가능 여부를 period/run/schema/설정/coverage로 한 번 계산하고 모든 KPI에 같은 포함 집합을 사용한다. 참고용 워크플로우는 남길 수 있지만 정량 AX/순위에서는 별도 집합·분모를 표시해야 한다. 0은 유효값, null은 미확정으로 유지한다. 설정 동수·미상 등급·분모 누락·정상 0·다른 설정의 합성 사례를 검증한다.

### R4 · P1 · 확정 — 표시 이름을 저장 경로와 사람 식별자로 함께 쓴다

- `core/owner.py:19`–`23`은 경로 문자를 `_`로 바꾸고 40자로 절단한다. `export.py:56`–`58`, `teamup.py:296`, `:541`–`542`가 그 값을 저장 키로 쓴다. `aggregate.py:315`·`:508`은 owner를 집계 키로 사용한다.
- 재현: 합성 계정 `a.b`와 `a_b`는 모두 `a_b`다. 앞 40자가 같은 서로 다른 두 이름도 같은 값이다. 두 입력이 같은 저장 폴더를 가리킨다는 점은 확정이다. 실제 동명이인/복수 PC 충돌 빈도와 현장 덮어쓰기 이력은 조사하지 않았다.

- 완료 기준: 생성 후 유지하는 member_id와 display_name, device_id를 분리한다. 같은 사람의 복수 PC 합산/택일 정책과 이름 변경 이력을 정의한다. 동일 이름의 두 사람이 별개로 남고, 서로 다른 경로 이름이 같은 ID면 중복 집계를 차단해야 한다. 기존 폴더 이전 시 충돌은 사용자에게 표시한다.

### R5 · P1 · 확정 + 재생성 한계 — 공유 결과 파일이 서로 다른 실행으로 섞일 수 있다

- `teamup.py:558`–`564`는 각 파일을 최종 위치에 바로 쓴다. `member.json`을 마지막에 쓰고 실패를 반환해도 먼저 바뀐 파일은 되돌리지 않는다. `export.py:95`–`101`도 staging 후 파일을 하나씩 교체하므로 교체 중 실패 때 묶음 전체 롤백은 없다. `export.py:108`의 '이전 결과 그대로 유지' 설명은 이 경우 성립하지 않는다.

### R6 · P2 · 확정 — 배분표의 보조 과제 코드가 분할 집계 결과에서 빠진다
