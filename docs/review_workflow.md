# LM25 업무·AI 흐름 설계 검토

검토일: 2026-09-09. 대상은 현재 `LoadMonitor25` 소스이며 기준은 활동 근거에서 신뢰도와 한계를 드러내는 업무 투입 분석, 추적 가능한 업무 흐름, 검증 가능한 자동화 후보 제공이다. 업무·AI 영역의 결론은 **기능 배치는 목적에 맞지만 결과를 확정하는 계약이 부족하여 조건부 적합**이다. 특히 비업무 제외, 업무 신원, 실제 근거 연결, 부분 완료, 사용자 병합 금지의 일관성을 먼저 고쳐야 한다. 지금 결과는 검토할 초안으로 쓸 수 있으나 개인 업무량·자동화 우선순위를 확정하는 근거로 쓰기에는 아래 결함이 남아 있다.

제품 소스, 실제 데이터·보고서, 개인 설정은 수정하지 않았다. `judge.py`, `refine.py`, `agentic.py`, `flow.py`, `retag.py`, `core/details.py`, `core/projmap.py`, `tools/copilot_auto.py`, 배포 과제 목록 `config/agentic_tasks.json`을 읽었다. 앱 진입점·수집·브라우저·Copilot·네트워크는 실행하지 않았다. 선택한 AST 함수와 순수 코드 구간을 합성 입력으로 실행했으며 근거 파일을 만드는 단일 검증은 TEMP의 합성 파일을 사용하고 제거했다. [재현 관찰값](review_workflow_evidence.json)은 개선 성공을 나타내는 회귀 기대값이 아니다.

## 핵심 문제 6개와 완료 조건

### W1 · P1 · 미확정 AI 응답을 확정 판정으로 바꾼다 — 확정

`judge.py:701`은 업무 여부가 `y`로 시작하는지 검사하고 나머지를 전부 `False`로 만든다. 합성 응답의 `UNSURE`와 `null` 모두 비업무로 채택됐다. 이후 비업무 판정은 신호 제거와 `rehours_meta`로 이어진다(`judge.py:1583`). `flow.py:718`도 미정·오타·빈 자동화 등급을 모두 `중`으로 바꾼다. 기존 재현기의 없는 근거와 `UNSURE` 단계가 그대로 중간 자동화 등급으로 저장되는 결과를 재확인했다.

개선: 업무 여부와 자동화 등급을 엄격한 enum으로 검증하고, 잘못된 값은 `needs_review`와 별도 원인으로 남긴다. 재시도 또는 규칙 임시값을 사용하더라도 AI 확정과 구분한다.

완료 조건: `y/n`, `상/중/하` 정상값만 확정된다. `UNSURE`, `null`, 빈 값, 임의 문자열, 잘못된 자료형은 업무시간을 제거하거나 자동화 우선순위에 참여하지 않는다. 정상·미확정·실패 상태가 파일과 개인·팀 화면에서 동일하게 읽힌다.

### W2 · P1 · 정제에서 비업무를 빼도 그 MM을 다른 업무에 옮긴다 — 확정

`refine.py:646-647`은 `w:false` 그룹을 정제 결과에서 제거하지만, `refine.py:693-703`은 원본 전체 MM을 남은 share에 재배분한다. 합성 입력 `업무 0.2 MM + 비업무 0.8 MM`에서 비업무를 제외하자 남은 업무가 **1.0 MM**으로 변했다. 정제는 `signals`와 `mm_meta`를 같은 작업에서 갱신하지 않으며 워크플로우는 원본 신호와 원본 업무 행을 읽는다(`flow.py:192`, `flow.py:206`). 정제표에서 사라진 일이 후속 흐름의 재료로는 남는 구조다.

개선: 단순 표시 제외, 미배분 처리, 실제 비업무 시간 제거를 구분한다. 비업무 확정이면 원신호 식별자로 판정 단계의 제외·시간 재산정 경로에 전달하고 해당 결과에 의존하는 정제·후보·흐름을 함께 다시 만든다. 신호 가중치의 0.8 MM을 곧바로 실제 제거할 시간이라고 가정하지 않는다. 실제로 제거할 시간은 측정 영역의 구간 정책이 결정해야 한다.

완료 조건: 정제 전후 원본 MM·제외된 추정량·남은 추정량·재산정 총량을 대사할 수 있고, 비업무의 몫이 생존 업무로 조용히 이동하지 않는다. 같은 제외가 반복되어도 중복 차감되지 않으며 원신호·정제표·흐름·개인·팀 보고서가 동일한 판정 버전을 사용한다.

### W3 · P1 · 업무명이 다른 과제의 동명 업무까지 연결한다 — 확정

프롬프트는 과제와 업무를 함께 보여주지만 응답에는 세부업무 이름만 요구한다(`agentic.py:171`, `agentic.py:182`). `_row_index`는 과제를 생략한 Level 3도 색인하고 부분일치까지 허용한다(`agentic.py:358-390`). 합성 자료의 과제 A 0.2 MM과 과제 B 0.8 MM에 모두 `design review`가 있으면 이름 하나를 받은 후보에 **1.0 MM, 근거 행 2개**가 붙는다. `row_sig`는 이어서 실행하기 위한 문자열일 뿐 AI 왕복·근거 연결의 안정 ID가 아니다.

개선: 신호 ID → 원본 업무 ID → 정제·병합 계보 → 후보의 업무 ID → 흐름 단계의 신호 ID를 유지한다. 이름은 표시와 검색 보조에만 사용한다. 과제명이 없는 동명 응답은 보류한다.

완료 조건: 과제 A의 업무 ID만 선택하면 0.2 MM만 연결한다. 동명·부분일치·띄어쓰기·개명·병합·분리 후에도 다른 업무의 MM을 가져오지 않는다. 기존 이름 기반 캐시는 자동 확정 이관하지 않는다. 관련 업무량/중복 제거 업무량/예상 절감량의 공통 표시 계약은 보고서 담당 개선과 연결한다.

### W4 · P1 · 근거 문장을 원신호와 검증하지 않고, 없는 과제 근거도 보낼 수 있다 — 확정

`flow.py:716`은 AI의 evidence 문자열을 길이만 잘라 보관한다. 원신호 ID, 같은 업무·기간 여부, 실제 존재 여부를 확인하지 않는다. 요청→산출 페어는 과제 전체의 표본이라 담당 업무가 다를 수 있음을 주석으로만 설명한다(`flow.py:346-349`). 정제에서도 signals가 없고 `_evidence_slice`가 과제 단락을 찾지 못하면 `self.ev`의 앞부분을 보낸다(`refine.py:442`). 합성 입력에서 Wanted project에 Unrelated project의 원문이 포함됐다. 정렬 불가라는 경고는 있었지만 근거의 범위를 보장하지 못한다.

개선: signals가 없으면 정렬된 근거 없음으로 처리하고 무관한 evidence 폴백을 제거한다. 단계별 `evidence_ids`를 해당 단위·기간의 허용 집합과 대조하고, 실제 관찰과 AI가 제안한 일반적 단계를 구분한다. 같은 과제 다른 업무의 페어는 보조 맥락으로만 전달한다.

완료 조건: 정상 ID, 없는 ID, 다른 과제 ID, 다른 기간 ID, 같은 과제의 다른 담당 업무 ID, 빈 signals를 검증한다. 검증되지 않은 단계·주기·자동화 근거가 확정 흐름과 우선순위에 참여하지 않는다. 상세 설명의 출처를 사용자가 원신호까지 따라갈 수 있다.

### W5 · P1 · 잘린 답의 일부 회수를 전체 판정 완료로 기록하고, 변경된 근거를 승계한다 — 확정

Agentic은 잘린 JSON에서 내용 하나라도 복구되면 통과시킨 뒤(`agentic.py:656-700`), `absorb`에서 보낸 모든 새 행을 `rows_done`에 넣는다(`agentic.py:668-669`). 후보 하나가 복구된 합성 응답에 입력 업무 두 개를 주면 두 행 모두 완료, `partial=False`가 됐다. 신규 후보·오할당 답이 중간에 사라졌는지 구분할 수 없다. 또한 재개 조건은 기간·행 수·파일명·`과제|업무|유형|MM`뿐이다(`agentic.py:153-156`, `agentic.py:622-624`). 설명/근거만 바꾸면 같은 서명이 나온다. 흐름 재개도 단위 이름과 최소 단계 수만 보고 이전 내용을 승계한다(`flow.py:973-987`).

개선: 각 입력 ID의 `processed`/`no_match`/`needs_review` 확인과 응답 완결 여부를 별도로 기록한다. 복구된 항목은 보존하되 빠진 판정은 미완료로 둔다. 입력 신호·행·설정·과제 목록·별칭·프롬프트·알고리즘 버전의 해시를 파생 결과에 기록하고 관련 입력 변경 시 재개 캐시를 무효화한다.

완료 조건: 정상적인 빈 match는 명시적 무매칭으로 완료할 수 있지만, 잘린 답·한 입력 누락·신규 후보 절단·오할당 절단은 완전 성공이 되지 않는다. 동일 이름/행 수/소수점 MM에서 원문·설명·과제 정의·별칭을 바꾼 경우 해당 결과를 다시 판정한다. 실패한 재실행이 이전 결과를 보존하더라도 화면은 최신 성공처럼 표시하지 않는다.

### W6 · P1 · 이미 저장된 병합은 새 `never` 제약을 우회한다 — 확정

`project_merge_map`은 기존 pmap을 먼저 읽고(`core/details.py:821`), 새 점수 그래프와 클러스터에 제약을 적용한다. 그러나 이미 저장된 간선을 제거하거나 결과 전체를 현재 제약에 대조하지 않는다(`core/details.py:878-907`). 합성 캐시 `Alpha→Beta`와 `never=[Alpha,Beta]`를 함께 주면 거부 사유에는 never가 기록되지만 반환 맵에는 **Alpha→Beta가 그대로 남는다**. 이전에 병합한 두 과제를 나중에 각각 사용자 지정해도 같은 유형의 위험이 있다(후자는 조건부 위험으로 정적 검토만 수행).

개선: 현재 규칙·사용자 지정·never를 기존 캐시를 포함한 전체 클러스터에 적용한다. 자동 추론 별칭과 사용자가 확정한 별칭의 출처를 분리하고 충돌을 명시한다. 현재 이름 목록 밖의 캐시 대표를 통한 간접 합류도 검사한다.

완료 조건: 저장된 직접/간접 간선 뒤에 never를 추가하거나 두 과제를 사용자 지정하면 금지 쌍이 실제 결과에서 분리된다. 기존 캐시를 합친 최종 무리가 상한 5를 넘지 않는다. 캐시 없음/있음, 입력 순서, 동일 자료 재실행, 잘못된 캐시를 포함한 합성 사례를 통과한다. **캐시 없는** `cluster2`의 간접 금지 및 상한 5는 이번 합성 검증에서 이미 통과했다.

## 유지할 좋은 설계 3개

1. **계산과 AI 설명의 분리.** Agentic은 MM을 프롬프트에서 제외하고 코드가 업무 행으로 관련량을 다시 계산한다(`agentic.py:133-136`, `agentic.py:393-483`). 흐름도 AI 숫자 대신 자료의 MM을 붙인다(`flow.py:747-748`). 안정 ID와 집계 계약을 보강하되 이 분리는 유지해야 한다.
2. **보수적 병합과 인간 교정.** 과제 범위 안 세부 병합, 금지 쌍을 무리 전체에 적용하는 cold clustering, 상한 5, 혼재 표시, 사용자 상위 지정 우선은 목적에 잘 맞는다(`core/details.py:701-765`, `flow.py:330-343`). 캐시 적용 뒤에도 같은 성질을 보장하는 쪽으로 확장한다.
3. **운영 실패를 드러내려는 구조.** 묶음 분할, 적응 재시도, fatal 중단, 미판정/얕은 신호/실패 통계, 이전 결과 보존은 현장 사용을 고려한 설계다(`judge.py:748-800`, `agentic.py:704-765`, `flow.py:1090-1108`). 출력 일부 회수와 의미상 완료를 분리하면 더 신뢰할 수 있다.

## 수정 순서와 검증 범위

1. W1/W2: 미확정·비업무 상태 계약과 제외 후 재산정 경로부터 통일한다. 측정 담당의 제외 후 시간잔류, 보고서 담당의 총량 대사를 연결한다.
2. W3/W4: 안정 ID와 같은 업무·기간의 근거 검증을 공통 스키마로 만든다. 후보·흐름·정제·오할당 제외를 같은 계보로 묶는다.
3. W5/W6: 입력/설정 버전별 부분 완료·재개 계약을 적용하고, 최종 병합 결과에 사용자 제약을 다시 검사한다.
4. 이후 자동화 적합도 기준과 후보의 입력·출력·예외·접근 가능 데이터/API·검증자·기준 성능·실측 절감량을 구조화한다. 계획 과제 설명에 적힌 목표 KPI를 관찰된 절감량으로 전환하지 않는다.

합성 검증은 현재 6개 신규 결함 동작과 기존 3개 재현을 확인하고 cold clustering 제약 한 묶음을 통과했다. 실제 AI 왕복 품질, 사내 브라우저 선택자 안정성, 실데이터 오분류율, 화면 클릭 및 보고서 E2E는 이번 범위 밖이다. 제품 행동을 바꾸지 않았으므로 배포 파일 목록 갱신은 필요하지 않으며, 제품 린트 성공을 이 결함들의 해소로 해석해서는 안 된다.
