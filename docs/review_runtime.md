# LM25 실행·운영·배포 설계 검토

2026-09-09. `run.py`, `ui/app.py` 실행/API, `teamserver.py`, 내장 Python 설치·이동·패키징 도구, 프로젝트 린트·훅을 검토했다. 제품 소스는 변경하지 않았다.

**판정: Windows 현장 실행과 배포를 돕는 구성은 적절하다. 다만 실행 상태·프로세스 소유권·팀 결과 묶음의 일관성을 보완해야 한다.** 아래 재현은 선택한 원본 AST 함수에 대체 I/O와 합성 입력을 주입한 결과다. 실제 UI/서버/수집/브라우저/업로드를 실행한 결과가 아니다.

## 핵심 문제와 완료 조건

### O1 · P2 · `--no-teams`가 Graph 호출을 막지 않는다

`run.py:589`의 Graph 조건은 `clientId`만 검사한다. 뒤의 웹·Copilot·창 읽기 분기는 `--no-teams`를 검사한다. 선택한 `main`에 합성 clientId와 `--collect-only --no-teams`를 주면 Graph 단계 호출이 한 번 기록된다. 실제 Graph 요청은 보내지 않았다.

모든 Teams 경로의 공통 입구에서 옵션을 적용한다. 해당 옵션이면 Graph·웹·AI·UIA 호출이 모두 0이어야 한다.

### O2 · P2 · 부분 실패와 최종 성공을 분리하지 않는다

`run.py:620`–`:626`은 수집만 모드에서 최종 완료를 true로 기록하고 0을 반환한다. 합성 검증에서 직접 `step` 6개를 모두 False로 주입해도 동일했다. Outlook/폴백은 무동작 대체 함수이므로 모든 실제 수집기가 실패한 실험으로 일반화하지 않는다. 일반 실행도 단계별 실패 기록과 별도로 마지막 완료 true를 기록하며, UI `run_job`은 반환 코드 0이면 완료 문구를 남긴다(`ui/app.py:1534`). 개별 오류 기록은 있으므로 실패가 전혀 표시되지 않는다는 뜻은 아니다.

단계별 성공/부분/실패/설정상 제외 및 필수 입력 충족 여부를 집계해 최종 상태와 보고서 사용 가능 범위를 반환한다. 수집 전부 실패, 선택 소스만 실패, AI 일부 실패를 각각 검증한다.

### O3 · P2 · API에 JSON 배열을 보내면 실행 중 상태가 남는다

`ui/app.py:4052`–`:4073`은 JSON 문법만 검사하고 `JOB.running=True` 뒤 `b.get`을 호출한다. 합성 `[]` 입력에서 AttributeError, 응답 없음, running=true가 확인됐다. 브라우저의 정상 버튼 요청은 객체이므로 정상 클릭만으로 이 문제가 생겼다고 주장하지 않는다.

JSON 객체·필드 타입·기간을 먼저 검증하고 작업 스레드 시작 실패도 상태를 복원한다. 잘못된 입력은 400을 반환하고 다음 정상 실행이 가능해야 한다. 같은 설치 폴더의 동시 실행도 단일 작업 ID/프로세스 간 잠금으로 관리한다.

### O4 · P2 · 다른 설치본의 Copilot 브라우저도 종료 대상으로 잡힌다

`ui/app.py:52`–`:59`는 모든 msedge.exe 중 명령줄에 `copilot_profile`이 들어가는 프로세스를 종료 대상으로 선택한다. 현재 ROOT·실제 프로필 경로·생성 PID 검사가 없다. UI 시작(`:4923`)과 종료에서 호출되며, `tools/Prepare-Move.ps1:136`에도 같은 범위가 있다. 명령 캡처로 선택 범위를 확인했으며 실제 프로세스는 종료하지 않았다.

실행한 설치/작업의 PID와 정확한 정규화 프로필 경로를 기준으로 종료한다. LM24/LM25 또는 두 LM25 폴더를 함께 쓰는 합성 프로세스 목록에서 자신의 프로세스만 선택되어야 한다.

### O5 · P1 · 서버 저장은 파일별 교체이며 묶음 전체 교체가 아니다

`teamserver.py:366`–`:432`에는 staging·백업·실패 복원이 있지만 최종 파일을 하나씩 바꾼다. 개인별 저장 잠금(`:498`)과 취합 잠금(`:176`)은 서로 다른 영역이다. 한 사람의 업로드 도중 다른 요청의 취합이 같은 폴더를 읽는 것을 이 잠금들이 막지 않는다.

TEMP 합성 검증에서 첫 파일의 교체 직후 관찰 콜백으로 첫 파일=new, 두 번째 파일=old, member=old를 확인했다. 정상 저장이 끝나면 새 묶음이 된다. 이는 중간 혼합 상태가 존재한다는 증명이며, 실제 동시 서버 장애나 최종 보고서 오염을 실행으로 재현했다는 뜻은 아니다. 공유폴더 경로의 실패 후 혼합 상태는 별도로 보고 검토 R5에서 재현했다.

모든 파일을 실행별 불변 폴더에 완성·검증한 뒤 현재 실행 포인터 하나를 교체한다. 독자는 고정한 실행만 읽는다. 동시 업로드·취합·중간 실패 시험에서 완전한 이전/새 묶음만 보여야 한다.
