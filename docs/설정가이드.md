# LoadMonitor30v1 설정 가이드

모든 설정은 **`config\config.json`** 한 파일입니다. 메모장으로 열어 고치면 되고,
저장 후 다음 [분석 실행]부터 반영됩니다(서버 재시작 불필요).

JSON 규칙 세 가지만 주의하세요.
- 문자열은 큰따옴표 `"..."`
- 항목 사이에는 쉼표 `,` (마지막 항목 뒤에는 쉼표 없음)
- 경로의 백슬래시는 두 번 `\\` → `"D:\\작업\\설계"`

> **팀 서버 주소만은 config.json 이 아닙니다.** 결과를 보낼 팀 서버의 IP·포트는 `LoadMonitor30v1-팀서버주소.bat` 으로 바꿉니다
> (§5-0 팀 서버 주소 바꾸기). 바꾸지 않으면 [분석 실행]이 끝날 때 기본 팀 서버로 자동 보고됩니다.

## v3 구조 — 무엇이 달라졌나 (한 페이지)

> **[로컬PC 자료수집]은 이 PC에만 있는 자료만 모읍니다(분석·팀 서버 보고 없음).** PC 가동 기록·파일·최근 문서·git·
> 프로그램 기록만 읽어 빨리 끝납니다. 메일·일정·팀즈는 PC가 아니라 회사 계정에 있는 자료라 읽지 않습니다 — 같은 계정이면
> 폴더를 받은 마지막 PC(클라우드 PC)의 [분석 실행]이 기간 전체를 한 번에 읽습니다.
> 이 PC와 분석할 PC의 계정이 다르거나 분석할 PC에서 메일·팀즈를 읽을 수 없을 때만 `collectOnlyMailTeams: true`로 둡니다.
> 그때는 [분석 실행]과 같은 경로로 읽고, Copilot 경로는 `collectOnlyHeadless`(기본 true = 생략)를 따릅니다.
> [분석 실행]은 로컬PC 자료수집 + AI 분석 + 팀 서버 보고(자동, 실패하면 알림)를 한 번에 합니다(§5-1).

v24 계열에서 같은 증상(PC 시간 오표시·정체·상위 분류 흔들림)이 판마다 재발해, v3 는 증상이 아니라
**구조**를 바꿨습니다. 사용할 때 알아두면 좋은 네 가지:

1. **PC 가동 기록은 원장입니다.** `data\pc\pc_spans.csv` 가 유일한 저장 원천(추가 전용)이고
   `pc_on.csv` 는 여기서 재생성되는 캐시입니다. 수집을 몇 번을 다시 돌려도 지난 기록이 깎이지
   않습니다. 이동해 온 PC 는 `pc_anchor.json`(첫 사용 시각)이 동기화된 브라우저 방문을 기록에서
   막습니다. 추이·하한·진단 줄이 **같은 숫자**를 봅니다.
2. **부분 완료는 종료 코드 2 입니다.** 시간 예산에 닿으면 그때까지를 저장하고 2로 끝납니다 —
   화면·기록에 '다음 실행이 이어서' 로 표시되고, **판정·Agentic 니즈 발굴은 내용 기준으로 남은 것만**
   다시 묻습니다(행 순서가 바뀌어도 이어집니다). 정제는 이름 병합 특성상 전량 기준입니다.
3. **단계 상태 파일**(`report\stage_state_<기간>_<단계>.json`)이 진행·중단 사유·남은 양을
   담습니다. 긴 Copilot 왕복 동안 출력이 없어도 30초 하트비트가 뛰므로, '느려서 조용한 것'을
   '죽은 것'으로 오인해 끊는 일이 없습니다. 화면의 '왜 비었나' 도 이 파일을 읽습니다.
4. **상위(Level 1) 어휘는 한 곳**(core\details 의 L1_META)에서 색·정렬·엑셀 단계·프롬프트가
   전부 파생됩니다. `level1Set` 에 범주를 더하면 화면 색·정렬·프롬프트에 자동 반영됩니다.
   lint 관문 8이 이 규칙 밖의 하드코딩 재출현을 막습니다.

## 1. watchFolders — 가장 중요 (파일·Recent 소스)

산출물(설계·문서·코드)이 실제로 저장되는 폴더를 나열합니다.
여기 없는 폴더의 작업은 잡히지 않습니다.

```json
"watchFolders": [
  "D:\\작업",
  "C:\\Users\\홍길동\\Documents\\프로젝트",
  "\\\\서버\\팀공유\\설계자료"
]
```
네트워크 드라이브도 됩니다(느릴 수 있음). 하위 폴더까지 자동으로 훑습니다.

- **공유·동기화 폴더**(`\\서버\…`, OneDrive/SharePoint 동기화 라이브러리)를 넣으면 동료가 저장한
  파일도 mtime 이 내려옵니다. 수집기가 `author`(Office 문서의 마지막 수정자, 그 외는 파일 소유자)를
  함께 적고, 분석은 `owner`·Windows 계정명·`teamsSelfNames` 와 다른 사람의 파일을 **'파일(타인)'**
  (과제 맥락용, 시간 근거·PC 하한 게이트 아님)으로만 남깁니다. 신호 출처 카드의 '제외 — 타인 저장 파일'
  에 건수가 보입니다.
- `.venv`·`site-packages`·`node_modules`·`__pycache__`·`.git`·`build`·`dist` 같은 패키지·빌드 폴더는
  기본으로 빠집니다(`excludePackageDirs: true`). pip/npm 설치 한 번이 수천 건의 '파일(코드)' 로 잡히던
  왜곡 방지 — 굳이 잡고 싶으면 `false`.
- 기본 확장자(`watchExtensions`)에 매크로 Office(`.xlsm .xlsb .pptm .docm`)·한컴 `.hwpx`·Visio `.vsdx`·
  LabVIEW `.vi`·OneNote `.one`·Outlook 항목 `.msg` 가 추가됐습니다. 예전 config.json 을 그대로 쓰는
  사람은 목록에 손으로 보태세요.
- 실행 때마다 관측한 (파일, 그때의 mtime) 은 `data\files\files_history.csv`·`recent_history.csv` 에 400일간
  누적됩니다 — 같은 문서를 여러 달 고쳐도 앞 달의 저장 근거가 남습니다(매월 실행할수록 이득).
- `author` 는 Office(OOXML) 문서의 `lastModifiedBy`, 공유·동기화 폴더의 그 밖의 파일은 NTFS 소유자로 채우고
  로컬 폴더의 PDF·CAD 등은 비웁니다(구분 불가·ACL 비용 회피, 큰 공유 폴더는 90초 예산). Recent 에는 `src`(lnk|mru)·
  `target_mtime`(대상 파일의 현재 수정 시각) 열이 생겨 **열람만 한 문서**(열람 시각이 수정 시각보다 늦음, Outlook 첨부
  캐시)를 '파일(열람)' 로 구분합니다 — 첨부 1건을 열어 본 날이 하루 9h 가 되던 과대 방지(§9 `viewCountsAsActive`).
  로그인된 Office 의 `User MRU` 키까지 읽어 M365 계정 PC 에서 MRU 가 0건이던 것도 고쳐졌습니다(`[recent] mru keys=N`).

## 2. excludePathKeywords — 필수 (개인정보 방어선)

경로·파일명에 이 키워드가 있으면 수집·리포트·AI 프롬프트 **전부에서 제외**됩니다.
본인 개인 폴더 이름을 반드시 추가하세요.

```json
"excludePathKeywords": ["개인", "가족", "이력서", "다운로드", "temp", "본인폴더명추가"]
```

매칭 규칙(파일·Recent·git 수집기와 분석이 같은 규칙):
- 경로 전용 토큰 `temp` `downloads` `임시` `다운로드` 는 **폴더 이름이 정확히 그것일 때만** — `Temperature_Test`,
  `temp_sensor`, `template` 폴더는 빠지지 않습니다(예전엔 부분 문자열이라 통째로 사라졌습니다).
- 영문 키워드는 단어 경계(`temp` ⊄ `attempt`), 한글은 부분일치(`개인` ⊂ `개인자료`).
- 무엇이 빠졌는지는 수집 로그의 `[files] 제외: temp 12폴더 340건` 줄과 `data\files_excluded.json` 에 남습니다.
  기대한 폴더가 안 잡히면 여기부터 보세요.

## 3. gitRepos — SW 개발 시간 회수 (선택)

```json
"gitRepos": ["D:\\src\\projA", "D:\\src\\projB"]
```
어디에 저장소가 있는지 모르면 자동 탐색이 찾아서 config에 넣어줍니다:
```
python collect\Get-GitActivity.py --scan D:\src
```

**git 실행 파일 요건** — 수집기는 `git.exe` 를 PATH → Git for Windows(`Program Files\Git\cmd`) →
GitHub Desktop → SourceTree → Visual Studio 내장 git 순으로 찾습니다. 어디에도 없으면 `[git] git 실행 파일
없음 — 커밋 신호 수집 불가` 를 찍고 그 단계를 **실패로 기록**하며 찾아본 곳을 `data\git_source.json` 에
남깁니다([수집 진단]·`python 자가점검.py` 도 같은 탐색 결과를 보여 줍니다; 기존 `git_commits.csv` 는 덮어쓰지
않습니다). 예전에는 이 경우 조용히 '커밋 0건'(단계 OK) 이라 GUI git 사용자만 커밋 신호가 통째로 빠졌습니다.
자동 탐색이 못 찾으면 전체 경로(또는 설치 폴더)를 적으세요:
```json
"gitExe": "C:\\Users\\홍길동\\AppData\\Local\\Programs\\Git\\cmd\\git.exe"
```
현재 체크아웃된 브랜치뿐 아니라 **모든 로컬·원격 브랜치**의 내 커밋을 로컬 시각으로 모읍니다
(`git_commits.csv` 의 `branch` 열). 저장소 경로에도 §2 의 제외 규칙이 걸립니다.

## 4. 창 샘플러 없음 (LM28)

LM30v1 에는 창 샘플러가 없습니다 — 상주 프로세스·예약 작업을 만들지 않고, 등록 bat·화면 버튼도 없습니다.
근무 시간은 **PC 켜기·끄기 기록**(이벤트 로그·브라우저 방문 시각 힌트)과 **활동 흔적**(산출물·메일·회의·커밋·팀즈·수동 기록)으로 계산합니다.
옛 판에서 옮겨 온 `data\activity\activity_*.csv` 가 있으면 분석이 그대로 읽습니다.

## 4-1. 프로그램 사용 이력 — 샘플러 없이 (LM28)

어떤 프로그램을 언제·얼마나 썼는지 참고 표로 보여 줍니다. 상용 프로그램(Ansys·Creo 같은 각종 시뮬레이션·CAD)과
비상용 프로그램(무료·오픈소스·자체 개발·프로토타입)을 나눠 셉니다. 샘플러·상주 프로세스·예약 작업·관리자 권한 없이 동작하고,
따로 설정할 것은 없습니다. **참고 지표라 투입 MM·로드율 계산에는 들어가지 않습니다.**

**세 가지 원천을 한 표로 합칩니다.**
1. **실행 기록** — [분석 실행]·[로컬PC 자료수집] 때마다 수집 단계 '프로그램 실행 기록 (참고)'(`collect\Get-ProgramUsage.py`)가
   Windows가 이 계정에 남긴 실행 흔적을 읽습니다. 실행 횟수, 창을 앞에 두고 쓴 시간(포커스 시간), 마지막 실행 시각,
   작업 표시줄 실행 횟수입니다. 1초 안팎이면 끝납니다.
2. **파일 흔적** — 이미 모은 파일·최근 문서 기록의 확장자로 셉니다. 예: `.wbpj` → Workbench, `.aedt` → AEDT,
   `.prt.3` → Creo, `.sldprt` → SOLIDWORKS, `.mph` → COMSOL, `.odb` → Abaqus.
3. **창 기록** — 옛 판의 창 샘플러 기록(`data\activity`)이 남아 있으면 그것도 읽습니다. LM30v1에는 샘플러가 없습니다.

**어디에 남나** — 실행 기록은 `data\programs\snap_날짜_시각.json`에 하루 한 장씩 남고, 최신 400장만 둡니다.
전체 경로는 남기지 않습니다. 실행 파일 이름과 위치의 종류(Program Files·사용자 폴더·다른 드라이브·네트워크 등)만 남깁니다.
개인·내려받기·임시 폴더(`excludePathKeywords`)에서 실행한 것은 이름도 남기지 않고 건수만 셉니다.

**어디서 보나** — 대시보드 'MM 산정 근거' 카드 아래 '프로그램 사용(참고)' 표, 분석리포트 1절, 리포트 7절(상세 표)입니다.
표에는 프로그램·구분(상용/비상용)·분류·출처·실행 횟수·포커스 시간·마지막 실행·파일 일수가 나옵니다.

**숫자 읽는 법**
- 첫 수집 날에는 스냅샷이 한 장뿐이라 '누적 N'(이 계정에 쌓인 전체)만 보입니다.
- 다음 날 수집부터는 두 스냅샷 사이의 증가분이 그 기간의 실행 횟수·포커스 시간이 됩니다. 증가분 구간은 기간 앞뒤로
  최대 36시간 넘칠 수 있어 표 위에 그 구간을 적습니다.
- 과거 기간을 고르면 마지막 실행이 그 기간 안인 프로그램만 '썼다'로 봅니다.

**자체·프로토타입(추정)** — 목록(카탈로그, `core\programs.py`)에 없는 실행 파일이 사용자 폴더·다른 드라이브·네트워크에서
실행된 것입니다. 설치·갱신·런처·드라이버와, 제거 프로그램이 함께 있는 설치본은 뺍니다. 무료 휴대용 도구가 섞일 수 있어
'추정'을 붙입니다. 이름은 개인정보 검사를 거친 것만 보이고, 걸린 것은 '이름을 가린 도구 N개'로만 나옵니다.
카탈로그 밖의 일반 설치 프로그램은 개수만 보입니다(사적인 앱 이름이 팀으로 나가지 않게). 그 이름은 이 PC의 스냅샷에만 있습니다.

**사내 도구에 이름표 붙이기(`programsExtra`)**
```json
"programsExtra": [
  {"match": "myfea", "name": "사내 해석기", "kind": "비상용", "cat": "해석"},
  {"name": "Simcenter STAR-CCM+", "ext": [".sim"]}
]
```
- `match`는 실행 파일 이름의 앞부분입니다(대소문자 무시).
- `ext`는 여러 도구가 쓰는 확장자(`.prt`·`.sim`·`.inp` 등)를 어느 도구로 셀지 정합니다. `match` 없이 `name`·`ext`만 적어도 됩니다.
  `name`이 카탈로그 이름과 같으면 공급사·상용 여부도 카탈로그를 따릅니다.
- `ext`로 정하지 않은 모호한 확장자는 실행 기록에 후보 도구가 하나만 보일 때만 그 도구로 셉니다. 아니면 '도구 불명 파일'로만 보입니다.

**한계**
- 실행 기록은 탐색기·시작 메뉴·작업 표시줄로 띄운 실행만 셉니다. 다른 프로그램이 띄운 솔버(Workbench가 부르는 MAPDL 등)는
  덜 잡힐 수 있고, 파일 흔적이 일부를 메웁니다. 수집 줄의 'BAM 권한 없음(건너뜀)'은 보통 사용자 PC에서 정상입니다.
- '앱 실행 추적'(Windows 설정 > 개인 정보 > 일반, 또는 회사 정책)이 꺼져 있으면 실행 횟수가 늘지 않습니다. 이때는 수집 줄과
  화면에 경고가 뜹니다.
- 팀 통합 보고서 9절은 아직 옛 꼴(창 기록 시간)이라, 실행 기록·파일만 있는 프로그램이 0.0h로 보일 수 있습니다.
  데이터는 팀으로 올라가 있습니다.
- 폴더를 다른 PC로 옮겨도 스냅샷마다 PC 표식이 있어 PC별로 따로 센 뒤 합칩니다.

## 월간 리뷰에 다른 달 일이 섞이던 문제 (LM23 에서 수정)

과거 달 리뷰에 **하지도 않은 최근 일**이 적히는 문제가 있었습니다. 원인이 네 가지였습니다.

1. **AI 채팅이 이어져 있었습니다.** 월별 리뷰는 판정이 다 끝난 뒤에 만들어지는데, 그 Copilot
   채팅에는 이미 **분석 기간 전체**(최근 달 포함)의 신호가 들어 있었습니다. 이제 달마다 새 채팅에서
   묻고, 신호에 연도를 붙이고, "목록에 없는 것은 그 달 일이 아니다"를 프롬프트에 못 박습니다.
2. **그 달의 뒷부분이 프롬프트에 없었습니다.** 표본이 90건인데 한 달 신호가 91~179건이면
   앞 90건만 나가 **월 후반이 통째로 빠졌습니다**(150건이면 17일에서 끊김). 근거를 못 받은 모델이
   빈 곳을 추측으로 메웠습니다. 이제 어느 경우에도 그 달 처음과 끝이 표본에 들어갑니다.
3. **팀즈 웹 수집이 메시지 본문의 날짜를 그 메시지 시각으로 썼습니다.** "지난 회의(6/12) 결론대로"
   같은 문장이 있으면 9월 대화가 6월 신호가 됐습니다. 이제 날짜는 화면이 알려 주는 머리 조각
   (타임스탬프·구분선)에서만 읽습니다. 창 읽기 수집기는 원래 그렇게 하고 있었습니다.
4. **메일 웹 수집이 회신 인용문의 날짜를 썼습니다.** 미리보기에 `2026년 6월 12일 … 님이 작성:`
   이 있으면 9월 회신이 6월 메일이 됐습니다. 같은 방식으로 머리 조각에서만 읽습니다.

덧붙여 AI 리뷰에 **그 달에 없는 과제 이름**이 나오면 그 항목만 버리고 콘솔에 알립니다.

3·4번은 **데이터 자체**가 잘못 들어간 것이라, 고친 뒤 그 기간을 **다시 수집·분석**해야 바로잡힙니다
(`data\m365\teams_web.csv` · `data\outlook\mail.csv` 를 지우고 [분석 실행]).

## 워크플로우는 한 번에 끝까지 판정합니다

담당자 워크플로우는 **한 번의 실행으로 모든 담당 업무를 판정**합니다. 미판정이 남으면
자동으로 마저 묻고, **한 회차에 하나도 늘지 않거나** 시간 예산을 넘길 때만 멈춥니다.
예전에는 자동 마무리가 2회차 고정이라 그래도 남으면 [이어서 분석]을 사람이 다시 눌러야 했습니다.

그래도 미판정이 남았다면 화면이 두 가지를 구분해 알려 줍니다.

- **[이어서 분석] 버튼이 보이면** — 시간 예산이나 묶음 상한에 걸려 끊긴 것입니다. 누르면 이어집니다.
- **버튼이 [워크플로우 재분석] 이면** — 더 늘릴 수 없어 멈춘 것입니다. 다시 눌러도 같습니다.
  그 단위는 신호가 얕거나(§`MIN_SIGNALS`) 판정 응답이 그 이름을 돌려주지 않는 경우입니다.

| 설정 | 기본 | 뜻 |
|---|---|---|
| `flowBudgetMin` | 120 | 전체 시간 예산(분). **0 이면 무제한**(끝까지 갑니다) |
| `flowMaxChunks` | 400 | 묶음 수 상한 — 폭주 방지용 최후 방어선 |
| `flowUnitsPerChunk` | 10 | 한 왕복에 담을 업무 수 상한(실제 제동은 답 길이 예산) |
| `flowFinishRounds` | 12 | 미판정 자동 마무리 회차 상한. **0 = 마무리를 하지 않음**(남은 것은 [이어서 분석]) |
| `flowFinishMinGain` | 2 | 한 마무리 회차에서 이만큼도 늘지 않으면 멈춥니다 — 1 로 두면 예전(끝까지) 동작 |
| `flowFinishMaxAsk` | 3 | 같은 업무를 마무리에서 다시 묻는 횟수 상한 |
| `aiStageBudgetMin` | 120 | 판정·정제·Agentic 니즈 발굴 한 단계의 시간 예산(분). 0 = 끔. 닿으면 그때까지의 결과를 저장하고 멈춥니다(다시 실행하면 이어서) |
| `aiTotalBudgetMin` | 300 | 한 번의 [분석 실행] 전체(판정+정제+Agentic+워크플로우) 마감(분). 0 = 끔 |
| `aiStageStallMin` | 15 | 한 단계가 이 시간 동안 **출력도 상태 파일 하트비트도 없으면** 중단(분). 0 = 끔 |
| `aiStageNoProgressMin` | 45 | **진행률이 이 시간 동안 늘지 않으면** 중단(분). 0 = 끔. 오래 걸리는 정상 판정은 살리고, 멈춘 것만 끊습니다 |
| `aiStageMaxMin` | 0 | 진행 중이어도 이 시간을 넘기면 끊는 절대 상한(분). **0 = 끔**(기본). 켜 두면 오래 걸리는 정상 판정도 끊기고, 그러면 정제·Agentic·워크플로우가 건너뛰어집니다 |

분석 실행과 대시보드는 정상 진행에 타임아웃을 걸지 않습니다 — 끊는 것은 위 예산과, **멈춘 것을 알아보는**
정체 감지(`aiStageStallMin`)뿐입니다. 한 단계가 그 시간 동안 한 줄도 내지 못하면 그 프로세스와 그 아래
Edge·드라이버까지 끊고 "정체 감지" 로 적습니다(예전에는 그대로 영구히 기다려 화면이 '실행 중' 에서
벗어나지 못했습니다 — 제보 '무한 정지'). 진행 중에는 2분마다 경과·마지막 출력 시각이 찍힙니다.
업무가 아주 많아 오래 걸린다면 `flowBudgetMin` 을 늘리거나 0 으로 두세요. 반대로 **한 번에 오래 붙잡고 있는 것이
싫다면** 그 값을 30~45 로 낮추세요 — 그때까지 판정한 것은 저장되고, 화면의 [이어서 분석]이 남은 업무만 잇습니다.

> 2026-09-14 수정 — 이 세 설정(`flowBudgetMin`·`flowMaxChunks`·`flowUnitsPerChunk`)은 그전까지 **읽히지
> 않았습니다**. 최상위 키인데 코드가 `copilotAuto` 안만 보고 있어서, 안내대로 값을 바꿔도 항상 기본값(120분)이
> 쓰였습니다. 같은 수정으로 마무리 회차에 이득 문턱·연속 실패 차단·같은 업무 재질문 상한이 생겼습니다 —
> "미판정이 회차마다 한 개씩만 늘면서 두 시간을 쓰는" 상태가 스스로 멈춥니다.

## 활동 추이가 '올해' 가 아니라 몇 주짜리로 보이거나 비어 보일 때 — LM24_v2 (2026-09-13)

## PC 를 옮길 때 오래 걸리던 문제 — LM24_v2

원인은 '데이터가 많아서'가 아니라 **폴더 하나**였습니다. `data\copilot_profile`(Copilot 로그인용
Edge 프로필)이 **파일 수의 94%·용량의 96%** 를 차지합니다(실측 8개 설치본 100~529MB). 정작
옮겨야 할 수집 자료와 보고서는 **0.06~0.27MB** 입니다. 그 안은 Edge 가 새 PC 에서 알아서 다시
받는 컴포넌트이고, **로그인 정보는 이 PC 에 묶여 있어 가져가도 살아나지 않습니다.**

### 이제 [PC 이동 준비]가 알아서 줄입니다

따로 하실 일이 없습니다. **[PC 이동 준비]** 를 누르면 옮기기 직전에 프로필을 정리하고,
줄어든 크기를 알려 줍니다. 그다음 **폴더를 탐색기에서 그대로 드래그**해 옮기시면 됩니다.

실측(LoadMonitor18): 프로필 **529.2MB / 2,507개 → 11.7MB / 418개**(98% 회수, 1초 미만).
폴더 복사도 같은 디스크에서 0.68초 → 0.09초로 줄었습니다(네트워크·USB 면 차이가 더 큽니다).

지우는 것은 Edge 가 다시 받는 컴포넌트·캐시와, 옮길 폴더에 있을 이유가 없는 **저장된 비밀번호·
자동완성·방문 이력**입니다. **로그인은 그대로 남습니다** — 쿠키와 토큰(`Default` 안)·
`Local State` 는 건드리지 않으므로 이 PC 에서 계속 쓰셔도 다시 로그인하지 않습니다.

> 규칙은 '지울 것을 나열' 하지 않고 **'남길 것만 남기는'** 방식입니다. Edge 는 판올림 때마다
> 새 컴포넌트 폴더를 만들기 때문에(ProvenanceData·Edge Wallet·Subresource Filter…) 이름 목록
> 방식은 반드시 낡습니다. 실제로 옛 목록은 529MB 중 244MB 밖에 걷어내지 못했습니다.

### 받는 PC 에서

폴더를 옮긴 뒤 **LoadMonitor30v1-UI.bat** 을 실행하면 됩니다. 지난 PC 의 수집 데이터는
`data\추가PC\` 로 자동 보관되고, 분석은 **모든 PC 를 합쳐** 계산합니다(중복은 자동 제거).

이때 **다른 PC 에서 온 Copilot 로그인 세션은 자동으로 정리됩니다.** 그 세션은 어차피 쓸 수
없는데(암호 키가 원래 PC 에 묶여 있습니다), 남아 있으면 웹 수집이 '로그인 필요' 가 아니라
'시간 초과' 로 끝나면서 화면에 엉뚱하게 '네트워크 문제' 로 보이고 **그 PC 의 메일·팀즈가

**[AI 연결 진단]** 으로 한 번 로그인하시면 됩니다.

압축을 풀고 **[AI 연결 진단]을 안 눌러도** 그대로 쓰실 수 있습니다.

| 누르는 것 | 로그인 없이 |
|---|---|
| [로컬PC 자료수집] · [팀 취합] · [재분석만] | 그대로 됩니다 (AI 와 무관) |

예전에는 로그인이 없으면 청크마다 왕복을 되풀이해 **28분을 헛돌았습니다.** 이제 첫 왕복에서
알아채고 **약 35초** 만에 "AI 판정을 건너뜁니다"를 알린 뒤 나머지를 규칙으로 처리합니다.
나중에 [AI 연결 진단]으로 한 번 로그인하고 **[재분석만]** 을 누르면 AI 판정만 이어서 합니다.

## 상위(업무 성격) 재배치 — LM24

담당자 워크플로우에서 **과제가 엉뚱한 상위 밑에 있거나 '상위 미분류'로 빠지는** 문제를 고쳤습니다.

원인이 넷이었습니다.

1. **상위 표를 병합 전 이름으로 세고 조회는 병합 후 이름으로** 했습니다. 그래서 합쳐진 과제 중
   **흡수된 쪽의 상위 표가 통째로 버려졌습니다** — 전체 MM 의 절반을 차지한 상위가 사라지고
   0.5 MM 짜리가 과제 전체를 대표하는 일이 생겼습니다. 이제 같은 축(병합 대표)으로 셉니다.
2. **상위에 신원 축이 없었습니다.** 상위는 4개 고정 범주인데, 중위·하위와 달리 AI 가 돌려준 문자열을
   검증 없이 저장했습니다. `기술내재화`(공백 없음)가 다섯 번째 상위처럼 화면에 떴습니다.
   이제 저장할 때와 읽을 때 모두 고정 범주로 스냅합니다(못 짚으면 빈칸 — 억지로 찍지 않습니다).
3. **표가 갈려도 무조건 1위를 찍었습니다.** 51:49 와 100:0 을 똑같이 다뤘습니다. 이제 1위가 **60%**
   에 못 미치면 상위를 **찍지 않고** 그 사실을 알립니다 — 워크플로우 탭에 "상위가 갈린 과제 N건 —
   재배치 필요"로 접혀 나오고, 카드 머리말도 `상위 혼재 — 재배치 필요`로 뜹니다.
   **표가 갈렸다는 것 자체가 신호입니다**: 서로 다른 성격의 일이 한 과제로 묶였거나, 상위 판정이
   행마다 갈린 것입니다. 억지로 하나를 고르면 그 사실이 숨습니다.
4. **사람이 고칠 수단이 없었습니다.** 중위·하위는 별칭 파일로 고칠 수 있는데 상위는 없었습니다.
   이제 `config\projects.json` 의 지정 과제에 상위를 적으면 투표를 이깁니다:
   ```json
   [{"name": "프로젝트A", "match": ["프로젝트a"], "level1": "신제품개발"}]
   ```

## 과제 병합을 클러스터링으로 — LM24

병합 판단을 **쌍 판정 + 그리디**에서 **가중 점수 + 제약 클러스터링**으로 바꿨습니다.

- 예전에는 근거를 **개수로 세고**(2개 이상) 그 앞에 **거부권**을 뒀습니다. 그래서 담당업무 집합이
  완전히 같은 두 과제가 "근거 부족"으로 거부되고, 이름이 닮고 제품이 같은 짝이 "담당업무 배타"로
  거부됐습니다 — **기간이 갈린 같은 과제가 바로 그 모습**이라 가장 안전한 병합이 가장 자주 막혔습니다.
- 이제 근거에 **가중치를 주어 합산**합니다. 절대 뒤집으면 안 되는 것(사용자가 `never` 에 적은 쌍,
  괄호 꼬리 상이, 숫자 토큰 상이, 둘 다 지정 과제)만 금지로 남고, 담당업무 배타·시간대 비겹침·
  진부분집합은 **감점**입니다 — 다른 근거가 충분히 세면 이깁니다.
- **거부가 우회되던 구멍을 막았습니다.** 예전에는 `never` 로 갈라 둔 두 이름이 **제3의 이름을 경유해**
  같은 무리가 됐습니다(쌍 단위 거부는 추이적으로 우회됩니다). 이제 제약을 **무리 안에서** 강제합니다.
- 무리 크기 상한도 이제 실제로 지켜집니다(예전 흡수 한도는 사슬로 우회됐습니다).
- 같은 자료면 **같은 결과**가 나옵니다 — 예전에는 MM 값만 달라져도 병합 결과가 갈렸습니다.
- 점수가 문턱 사이인 **애매한 쌍은 합치지 않고** 목록으로 보여 줍니다.

## 과제(중위) 이름 병합 — 워크플로우가 갈라지거나 겹칠 때

담당자 워크플로우에서 **같은 과제가 여러 장으로 갈라지거나 같은 업무가 두 번** 보이면
이 절을 보세요. 원인은 과제 이름의 표기 흔들림입니다 — AI 가 묶음마다 판정하다 보면
`설계 검토` / `설계검토` / `설계-검토` 처럼 띄어쓰기 하나가 달라지고, 그 순간 별개 과제가 됩니다.

LM23 은 분석 때마다 이것을 **후처리로 합칩니다**(`config\project_aliases.json`).

- **Copilot 왕복을 새로 쓰지 않습니다.** 표기 규칙과 이미 모아 둔 근거
  (정제 결과·담당 업무 집합·제품·신호 시간대)만 봅니다. 그래서 분석이 느려지지 않습니다.
- **띄어쓰기·하이픈·가운뎃점·대소문자만 다른 이름**은 그것만으로 합칩니다.
- 표기가 다르면 **서로 독립인 근거가 2개 이상**일 때만 합칩니다. 서로 다른 업무가
  한 카드에 섞이는 것이 이 기능의 유일한 심각한 실패라, 애매하면 합치지 않습니다.
- 다음은 근거가 몇 개든 **무조건 합치지 않습니다**: 괄호 꼬리가 다름(`(양산)`/`(선행)`) ·
  숫자 토큰이 다름(`2차`/`3차`) · 한쪽이 다른 쪽의 진부분집합인데 남는 낱말이 2개 이상 ·
  담당 업무가 하나도 겹치지 않음 · 신호 시간대가 아예 안 겹침 · 둘 다 지정 과제.
- 같은 단위가 두 번 판정된 흐름은 **단계가 많은 쪽만** 남깁니다. 단계를 합치지는 않습니다 —
  합치면 시간순이 깨지고 근거가 다른 신호를 가리키게 됩니다.

**담당 업무(하위) 이름도 같은 방식으로 한 겹 더 접습니다.** 예전에는 띄어쓰기·구분자만 봤는데,
실제 응답은 이렇게 흔들립니다 — 그래서 표기·구조만 보는 규칙 네 가지를 더했습니다.

| 규칙 | 예 |
|---|---|
| 꼬리 문장부호 무시 | `샘플 평가.` = `샘플 평가` |
| 앞부분이 같고 꼬리가 3자 이하 | `금형 수정` = `금형 수정 요청` |
| 어순 무시(조사 제거) | `설계 검증` = `검증 설계` |
| 낱말 하나 차이(공통 2개 이상) | `결과 분석` = `분석 결과 정리` |

여기서도 괄호 꼬리와 숫자 토큰이 다르면 무조건 합치지 않습니다 — `설계 검토 1차`/`2차`,
`검토(양산)`/`(선행)`, `설계`/`설계도`, `시험 준비`/`시험 결과 정리` 는 모두 그대로 둡니다.

무엇을 왜 합쳤는지는 **워크플로우 탭 위쪽의 접힌 줄**("이름 병합 N건 · 흐름 중복 제거 N건")에
표로 나옵니다. 콘솔에도 같은 내용이 찍힙니다.

**신호가 얕아 흐름을 만들지 않은 업무**(신호 3건 미만)는 예전에 콘솔에만 찍혀 화면에서 통째로
사라졌습니다. 이제 각 과제 머리말 옆에 "신호가 얕아 흐름을 만들지 않은 업무 N개" 로 표시되고,
마우스를 올리면 그 목록이 보입니다.

**잘못 합쳐졌으면** `config\project_aliases.json` 에서 그 줄을 지우세요. 다만 띄어쓰기만
다른 이름은 규칙이 다음 실행에 다시 합치므로, 영영 갈라 두려면 같은 파일의 `never` 에
쌍을 적습니다:
```json
{"map":   {"설계검토": "설계 검토"},
 "never": [["설계 검토", "설계검토 자동화"]]}
```
`never` 는 규칙보다 먼저 검사되므로 확실히 막힙니다. 반대로 **항상 이 표기를 쓰게** 하려면
`config\projects.json` 의 지정 과제로 등록하는 편이 낫습니다(§5-2).

> 같은 이름 축(`ukey2`)을 판정·정제 단계도 함께 씁니다. 예전에는 판정이 대소문자만 비교해서
> 새 표기가 `entities_*.json` 에 쌓이고 그것이 다음 분석의 후보로 되먹여져 **재분석해도
> 갈라진 채로 굳었습니다**. 그 고리를 끊었습니다.

## 팀즈 웹 읽기 — 팀즈가 0 건일 때 가장 먼저 (권장)

대시보드의 **[팀즈 웹 읽기]** 버튼입니다. 메일의 [Outlook 웹 읽기]와 같은 방식으로,
Copilot 이 쓰는 **전용 Edge 프로필**로 `teams.microsoft.com` 을 열어 채팅을 읽습니다
(`collect\Get-TeamsWeb.py`, 분석 실행에도 자동으로 끼어 있습니다).

- **팀즈 앱이 꺼져 있어도 됩니다.** 창 읽기(`Get-TeamsWindow.ps1`)는 화면에 실제로 그려진
  부분만 UI 자동화로 긁으므로 창 크기·테마·팀즈 버전에 따라 PC 마다 0 건이 되곤 했습니다.
  웹 경로는 화면 렌더가 아니라 문서 구조(role·data-tid·aria-label)를 읽어 그 편차가 없고,
  대화방마다 위로 되감아 **지난 날짜까지** 가져옵니다.
- **처음 한 번만** 그 Edge 창의 팀즈 탭에서 회사 계정을 선택/로그인하면 됩니다
  (Copilot·Outlook 웹과 같은 창이라, 이미 로그인했다면 그대로 동작합니다).
- LLM 을 거치지 않으므로 지어낸 행이 없고, 데이터는 PC 밖으로 나가지 않습니다.
- 결과는 `data\m365\teams_web.csv` 에 **누적**되며, Graph·창 읽기가 이미 잡은 메시지는
  대조해서 다시 적지 않습니다(경로가 겹쳐도 중복 계상 없음).

설정: `teamsWeb`(기본 true) · `teamsWebMaxChats`(기본 40 — 훑을 대화방 수, 최근 순) ·
`teamsWebBudgetSec`(기본 900 — 전체 시간 예산). 예산 안에 반드시 저장까지 끝내고, 남은
대화방은 다음 실행으로 미룹니다. 되감기는 두 번 연속 새 메시지가 없으면 그 대화에서 멈춥니다.
손으로 돌리려면:
```
python collect\Get-TeamsWeb.py --from 2026-06-01 --to 2026-06-30
```
수집 순서는 ① Graph → ② 웹 → ③ Copilot → ④ 열린 창 읽기이고, 앞이 되면 뒤는 건너뜁니다.

Copilot 이 "연결된 Microsoft Teams 데이터 조회 도구가 없어…"라고 답하는 계정(테넌트에 Teams 커넥터 없음)은 대시보드 [팀즈 웹 읽기]를 쓰세요.

**내가 보낸 메시지를 알아보게 하기(`teamsSelfNames`)** — 창 읽기는 보낸 사람 이름으로 내 메시지를
가립니다. `owner`·Windows 계정명·AD 표시명·'나/You' 는 자동으로 비교하지만, 팀즈 표시 이름이 그와
다르면(영문 이름, 성·이름 순서) 목록에 적으세요. 없으면 팀즈로 일한 날이 전부 '수신' 이 되어 PC 하한이
열리지 않습니다(재택 Teams 인력 로드율 절반 — 실측):
```json
"teamsSelfNames": ["홍길동", "Gildong Hong"]
```
같은 목록이 §1 의 동료 저장 파일 판정에도 쓰이며, 이름은 Copilot 프롬프트에 나가지 않습니다.
Graph·Copilot 경로도 같은 규칙으로 '팀즈(발신)' 을 판정하고, Graph 시각은 로컬 시각으로 저장됩니다
(예전엔 UTC 그대로라 낮 발신이 새벽 야근이 됐습니다).

Copilot 조회 불가는 자동으로 기록되어 다음 분석부터 헛왕복을 생략합니다. 회사가 커넥터를
켜준 뒤 재시도하려면 `data\m365\teams_copilot_unavailable.json` 을 지우세요.
창 제목 저장이 싫으면 `"storeWindowTitle": false`.

## 5-0. 팀 서버 주소 바꾸기

**결과를 보낼 팀 서버는 `LoadMonitor30v1-팀서버주소.bat` 하나로 바꿉니다.** LM30v1은 시험판이라 여기서 시험용 팀 서버 주소를
저장하기 전에는 결과를 보내지 않습니다(아래 '시험판 보호'). 첫 [분석 실행] 전에 아래를 합니다. 주소는 `config.json`이
아니라 설치 폴더의 `config\team_server.json`에 따로 저장되고, 대시보드에서는 바꿀 수 없습니다(보여 주기만 합니다).

1. `LoadMonitor30v1-팀서버주소.bat`을 더블클릭합니다. 창이 먼저 지금 쓰는 주소를 보여 줍니다 — 서버 IP·포트(각각 어디서 온 값인지:
   기본값 / team_server.json / config.json 의 옛 teamServerUrl), 업로드 주소, 그리고 그 주소가 이 PC인지 다른 PC인지.
2. '새 서버 IP (예: 10.0.0.5)'와 '새 포트 (1~65535)'를 차례로 묻습니다. 바꿀 값만 입력하고, 그대로 둘 값은 Enter만 누릅니다.
   - IP 칸에 `http://IP:포트`나 `IP:포트`를 통째로 붙여 넣어도 나눠 받습니다(포트 칸에 따로 적으면 그 값을 씁니다).
   - 서버 IP 대신 PC 이름을 적어도 됩니다. 전각 숫자는 반각으로 고쳐 받습니다.
   - 형식이 틀리면 '[teamaddr] 저장하지 않았습니다 — 사유'를 보여 주고 원래 주소를 그대로 둡니다. 두 칸 모두 Enter면 아무것도
     바꾸지 않습니다.
3. 저장되면 '[teamaddr] 저장했습니다'와 새 주소가 나옵니다.
4. '지금 이 망에서 팀 서버에 닿는지 확인할까요 [Y/n]'에서 Enter를 누르면 연결을 확인하고, n을 누르면 건너뜁니다. 사내망 밖이라
   닿지 않아도 주소는 저장돼 있습니다 — 서버에 닿는 망에서 다시 확인하면 됩니다.

- **팀 서버를 직접 켤 때** — 팀 공용 PC에서도 먼저 이 bat으로 서버 IP(그 PC의 IP)와 포트를 저장한 뒤 `LoadMonitor30v1-팀서버.bat`
  (또는 대시보드의 [팀 서버 시작])으로 켭니다. 서버가 켜져 있는 동안 포트를 바꿨다면 [중지] 후 다시 시작해야 새 포트로 열립니다
  (§5-2 방법 A).
- **팀원에게 나눠 줄 때** — 주소를 저장한 설치 폴더를 그대로 나눠 주거나, `config\team_server.json` 한 파일만 팀원 폴더의
  `config\`에 넣으면 팀원 PC도 같은 주소로 보고합니다. 폴더째 다른 PC로 옮겨도 주소가 따라갑니다.
- **기본 주소로 되돌릴 때** — `config\team_server.json`을 지웁니다.
- **한 번만 다른 곳으로 보낼 때** — `python teamup.py --upload --host <IP> --port <포트>`는 저장된 주소를 바꾸지 않습니다.
- **자동 보고를 끌 때** — `config\config.json`의 `teamUpload.autoReport`를 `false`로 둡니다. 그러면 [팀 서버 업로드] 버튼을 누를
  때만 보냅니다(§5-1).

### 시험판 보호 — 시험용 팀 서버 주소를 정하기 전에는 보내지 않습니다 (`teamUpload.requireSavedAddress`, LM30)

**LM30v1은 `config\team_server.json`에 저장한 시험용 팀 서버로만 보냅니다.** 기본 주소는 기존 팀 서버라서, 거기로 보내면 팀원
각자의 LM28·LM29 결과가 LM30v1 시험 결과로 덮이기 때문입니다.

- `teamUpload.requireSavedAddress`가 `true`(배포 설정 · 키가 없어도 켬)이면, 주소를 저장하지 않았거나 저장한 주소가 기본 주소와
  같을 때 [분석 실행] 끝 자동 보고·[팀 서버 업로드]·`LoadMonitor30v1-팀업로드.bat`이 보내지 않습니다. 결과 묶음은 대기로 남고,
  실패 알림·배너 없이 업로드 카드에 '자동 보고 건너뜀 — 시험용 팀 서버 주소 없음'이 남습니다. [연결 확인]은 그대로 됩니다.
- 시험용 팀 서버 주소를 `LoadMonitor30v1-팀서버주소.bat`으로 저장한 뒤 [팀 서버 업로드]를 누르면 밀린 묶음까지 보내집니다.
- `false`로 두면 예전처럼 기본 주소(기존 팀 서버)로도 보냅니다 — 그 서버의 LM28·LM29 결과를 덮으니 시험 중에는 바꾸지 마세요.
- **LM30과 견줄 때는 판마다 다른 시험용 팀 서버를 씁니다.** LM30과 LM30v1이 같은 시험용 팀 서버로 보내면 같은 팀원의 결과가
  나중에 보낸 판의 결과로 덮입니다. 서버 PC를 따로 두거나, 한 PC에서 LM30 폴더와 LM30v1 폴더의 팀 서버를 서로 다른 포트로 켜고
  판마다 자기 서버 주소를 저장하세요(`teamShareDir`을 정해 두었다면 그 폴더도 판마다 다르게 둡니다). LM30 폴더의
  `config\team_server.json`을 옮겨 왔다면 `LoadMonitor30v1-팀서버주소.bat`으로 LM30v1용 주소를 다시 저장합니다.

## 5-1. 팀 서버 보고 — [분석 실행]이 끝나면 자동으로 보냅니다 (LM28)

[분석 실행]은 로컬PC 자료수집 + AI 분석 + 팀 서버 보고를 한 번에 합니다. 보고에 실패해도 결과 묶음은 대기로 남아
잃는 것이 없습니다. 그때는 서버에 닿는 망(사내망)에서 버튼 한 번으로 밀린 것까지 보내면 됩니다.
[로컬PC 자료수집]·[Outlook 웹 읽기]·[팀즈 웹 읽기]는 보고하지 않습니다.

1. `LoadMonitor30v1-팀서버주소.bat` 을 실행해 팀 서버 **IP·포트**를 저장합니다(설치 폴더의 `config\team_server.json` — §5-0).
   팀장이 저장해 둔 폴더를 그대로 받았다면 이미 들어 있습니다 — 폴더째 옮기거나 복사해도 주소가 따라갑니다.
   대시보드 [팀 취합 업로드] 카드는 **올릴 주소**를 보여 주기만 합니다(화면에서는 바꾸지 않습니다).
2. [분석 실행]이 끝나면 `report\upload_pending\`에 기간별 묶음을 먼저 만들고, 이어서 팀 서버로 자동 보고합니다.
   서버에 닿는지 먼저 확인하고, 밀린 기간의 묶음도 함께 보냅니다.
   오래 기다리지 않습니다 — 닿는지 3초씩 최대 2번 보고 안 되면 바로 끝내고, 보낸 뒤 45초 안에 답이 없으면 다시 보내지 않고
   남은 묶음까지 대기로 남깁니다(서버에 이미 저장됐을 수 있고, 다음 실행 때 다시 보내도 덮어쓰기라 결과는 같습니다).
   그래서 자동 보고는 길어야 1분 남짓이면 끝납니다. 값은 `teamUpload.pingTries`·`pingTimeoutSec`·`timeoutSec`로 바꿉니다.
3. 성공하면 상태 글자가 '대기 중 · 팀 서버 보고 완료 (N건)'으로 바뀌고, 카드에 '마지막 팀 서버 보고' 줄이 남습니다.
4. 실패하면(사내망 밖·서버 꺼짐·서버 거부) 알림 창이 한 번 뜨고, 다음 성공까지 화면 위쪽에 빨간 배너가 남습니다.
   서버에 닿는 망에서 배너나 카드의 [팀 서버 업로드]를 누르면 밀린 것까지 보내지고 배너가 내려갑니다.
   대시보드를 열기 싫으면 `LoadMonitor30v1-팀업로드.bat`을 더블클릭해도 됩니다. 배너의 [닫기]는 그 실패만 숨깁니다.
5. 서버 대신 공유폴더를 쓰려면 [공유폴더로 저장](경로를 물어봅니다 — `teamShareDir` 기본값).

- `LoadMonitor30v1.bat`으로 돌렸다면 실패했을 때 콘솔 맨 끝에 `[!] 팀 서버 자동 보고 실패 — 사유`가 한 번 더 찍힙니다.
- AI 판정이 실패한 실행(Copilot 로그인 만료 등)은 자동 보고하지 않습니다. 규칙이 임시로 뽑은 결과가 팀 서버에 있던
  같은 기간 결과를 덮지 않게 하려는 것입니다. 이때도 알림 창과 배너가 뜹니다('AI 판정 실패로 보내지 않음'). 원인을 고친 뒤
  [분석 실행]을 다시 하면 보고됩니다. 그 결과를 그대로 보내려면 [팀 서버 업로드]를 누르세요.
- [AI 정제]를 끄고 돌린 실행도 자동 보고하지 않습니다(알림 없이 카드에 '건너뜀'만 남습니다).
- 자동 보고를 끄려면 `config.json`의 `teamUpload.autoReport`를 `false`로 두세요. 그러면 예전처럼 버튼으로만 보냅니다.
  옛 키 `teamUpload.auto`는 더 읽지 않습니다.

보내는 것은 그 기간의 판정 결과와 근거 신호 목록입니다 — **메일 제목·회의 제목·동료 이름이 포함될 수**
**있습니다**(개인 폴더 신호는 `excludePathKeywords` 로 이미 제외됨). 자동 보고는 버튼으로 보낼 때 뜨던 확인 창 없이 보냅니다.
사내망 전용으로만 쓰세요.

## 5-2. 팀 취합 — 결과를 어디에 넣나

취합은 **인원별 폴더 하나 = 한 사람**으로 읽습니다. 폴더 안에 그 기간 결과 파일들과
`member.json`(요약)이 함께 있어야 그 사람이 취합에 잡힙니다. `member.json` 이 없으면 그 폴더는
무시되므로, 파일만 복사해 넣으면 취합에 나타나지 않습니다.

```
<취합 위치>\
  홍길동\
    member.json                       ← 이게 있어야 인원으로 인식
    mm_rows_20260601-20260630.csv
    mm_rows_20260601-20260630_refined.csv
    signals_20260601-20260630.csv
    mm_meta_20260601-20260630.json
    pivots_20260601-20260630.json
    entities_20260601-20260630.json
    ai_narratives_20260601-20260630.json
    agentic_20260601-20260630.json
    workflow_20260601-20260630.json
  김철수\
    ...
```

### 방법 A — 팀 서버 (권장)

1. 팀 공용 PC 에서 먼저 `LoadMonitor30v1-팀서버주소.bat` 으로 **서버 IP(이 PC 의 IP)·포트**를 저장합니다.
   그다음 **대시보드의 [팀 서버 (이 PC 에서 켜기)] 카드에서 [팀 서버 시작]**(또는 `LoadMonitor30v1-팀서버.bat`).
   서버는 시작할 때 설정된 서버 IP 가 이 PC 의 주소인지 확인해 알려 주고, 카드에도 같은 판정이 보입니다.
   이 설치 폴더(또는 `config\team_server.json` 한 파일)를 팀원에게 나눠 주면 팀원도 같은 주소로 올립니다.
   처음 켤 때 방화벽 허용 창이 뜨면 허용해야 다른 PC 에서 접속됩니다.
   그 PC 의 `teamdata\` 가 위 그림의 <취합 위치>가 됩니다(자동 생성).
2. 각자 대시보드 **[팀 취합 업로드]** 카드에서 **올릴 주소**를 확인합니다
   (주소가 다르면 `LoadMonitor30v1-팀서버주소.bat` 으로 고칩니다). 그 뒤로는 [분석 실행]이 끝날 때마다
   자동으로 보고하고, 자동 보고가 실패했을 때만 [팀 서버 업로드]를 누릅니다(§5-1).
   전송이 끝나면 **어느 폴더에 담겼는지**(`저장 위치: ...`)가 함께 찍힙니다 — 이 PC 에 LoadMonitor
   폴더가 여럿이면 꼭 확인하세요.
   업로드가 들어오면 서버가 **취합을 자동으로 다시 계산**합니다. 서버는 받은 파일을 저장하자마자 답하고 취합은 뒤에서
   돌리므로('저장됨 — 팀 취합은 서버가 이어서 갱신합니다') 팀원은 취합이 끝나기를 기다리지 않습니다. 취합 중에 들어온
   업로드는 모아서 끝난 뒤 한 번 더 취합합니다. 팀 대시보드 제목 줄에 '취합 중'이 보이면 잠시 뒤 새로고침하세요.
3. 팀 대시보드: `http://<서버 IP>:<포트>` — 지금 주소는 `LoadMonitor30v1-팀서버주소.bat`이 보여 줍니다(리포트 `/report`, 팀 통합 보고서 `/full`).

### 방법 B — 공유폴더

서버를 켤 수 없으면 각자 **[공유폴더로 저장]** 으로 `<공유폴더>\<이름>\` 에 같은 묶음을 냅니다
(`config.teamShareDir` 를 적어 두면 기본값으로 뜹니다). 그 뒤 팀장이 취합을 돌립니다:

```
LoadMonitor30v1-팀취합.bat            (config.teamShareDir 를 읽어 뷰어까지 실행)
python aggregate.py \\서버\팀공유\LoadMonitor    (경로를 직접 줄 때)
```

### 방법 C — 손으로 옮기기 (망이 아예 분리된 경우)

분석한 PC 의 `report\upload_pending\<기간>.json` **파일 하나**를 USB 로 옮겨,
서버망에 있는 PC 의 같은 폴더(`report\upload_pending\`)에 넣고 그 PC 에서
**[팀 서버 업로드]** 를 누르면 됩니다. 이 묶음에는 보낼 파일과 이름이 모두 들어 있어,
대신 올려도 **원래 사람의 이름으로** 취합됩니다.

### 판이 섞인 팀 — 팀취합본만으로 로드율 다시 재기 (`LoadMonitor30v1-팀로드율재계산.bat`)

LM20 으로 올린 사람과 LM24 로 올린 사람이 한 팀에 섞여 있으면 원값(D)끼리는 비교가 되지 않습니다
(산식·달력·분석 시점 절단이 다릅니다). 팀에 올라온 두 파일(`signals_<기간>.csv` · `mm_meta_<기간>.json`)만으로
**모든 인원을 하나의 산식·하나의 달력으로 다시 재는** 도구가 있습니다.

1. `team_recalc.py` 와 `LoadMonitor30v1-팀로드율재계산.bat` 두 파일을 **팀 폴더**(인별 폴더가 있는 곳 — 팀 서버 PC 의
   `teamdata\` 또는 공유폴더)에 복사합니다. LoadMonitor24 폴더 안에서 그냥 실행해도 `teamdata\`·`teamShareDir` 를 찾습니다
   (본인 `report\` 는 인원으로 보지 않습니다).
2. bat 을 더블클릭합니다. 기존 `team_report.html` 등은 **건드리지 않고** `팀로드율_재계산_<시각>.html` 과 CSV 2개
   (`_월별.csv`·`_과제.csv`)가 새로 생깁니다. 다시 실행하면 새 시각으로 또 하나 생깁니다.
3. 보고서의 **C3** 열이 권장값입니다(능동 흔적 있는 평일 8h 바닥 + 09~18 밖 능동 세션 초과). **A**(출근일 하한)·
   **B**(근거가 덮은 시간)·**D**(그 판의 원값)를 나란히 두고, **판 배지**(LM20 추정 / LM24)와 **무흔적 평일(−부재)** 열을
   함께 읽습니다 — C3−D 가 크게 양수면 원 판이 PC 없이 세션만 재었을 가능성(흔적이 적은 근무 유형), 음수면 원 판이 수동 신호
   다리(LM20)·PC 가장자리로 더 잡았거나 **C3 가 보지 못하는 PC 가동·샘플러 구간을 원 판이 실측한** 경우입니다. C3 는 합성 참값보다
   3~16p 아래로 재는 하한 성격이라 −15p 안의 음수는 판 차이로 단정하지 마세요. signals 를 읽을 수 없는 인원(0바이트·Excel ANSI
   재저장 등)은 0% 가 아니라 빈칸 + 비고로 나오고, 가용 0 인 달(전월 부재)은 비율·팀 합계에서 빠집니다.
4. 팀 폴더를 인자로 줄 수 있습니다(끝의 `\` 는 빼세요): `LoadMonitor30v1-팀로드율재계산.bat "\서버\팀공유\LoadMonitor"` — 지정한 폴더가
   없거나 인별 폴더가 없으면 **실패**합니다(다른 폴더로 조용히 바꾸지 않습니다). 내장 연도표(2025~2027 설·추석·대체공휴일·선거일)에
   없는 임시 휴일은 `--holidays 2026-11-02` 처럼 덧붙입니다.

한계: PC 가동·샘플러 구간·연차 일자·회의 수락 여부는 팀에 올라오지 않아 어느 산식도 복원하지 못합니다. 능동 흔적이
없는 평일은 8h 가 붙지 않아 C3 = 근거 구간(수동 세션은 하루 60분까지)뿐입니다(무흔적 평일 중 부재 일수만큼은 연차일 것입니다).
기간 종료 전에 올린 자료는 분석 시점 이후 평일을 가용에서 빼고 '기간 미완' 으로 표시합니다(LM20 의 부재는 절단 비율로 배분).

  주소를 저장하세요. '서버 거부'·'보낼 수 없는 묶음'이면 아래 '보낼 수 없음' 항목을 보세요.

  바로 보내려면 [팀 서버 업로드]를 누르세요. 서버가 계속 느리면 팀 서버 담당자에게 서버 PC 상태를 확인해 달라고 하세요.

  다시 분석하거나 `config.owner` 를 고친 뒤 다시 누르면 됩니다. 필요 없으면 [버리기].

## 5-3. PC 를 2~3대 쓸 때 — 폴더 통째로 옮기기

분석이 끝난 폴더는 대개 **우리 자신이 잡고 있어** 그냥 옮기면 "사용 중" 오류가 납니다
(대시보드·팀 서버·Copilot 전용 Edge, 그리고 그 폴더를 열어 둔 탐색기 창).

**`LoadMonitor30v1-이동준비.bat`** 을 실행하거나 대시보드의 **[PC 이동 준비]** 버튼을 누르세요:

1. 우리 프로그램을 모두 종료합니다 (일반 Edge 는 건드리지 않습니다 — Copilot 전용 프로필만)
2. 탐색기가 그 폴더를 열고 있으면 **어느 창인지** 알려 줍니다
3. 폴더 이름을 잠깐 바꿔 **정말 옮길 수 있는지 실제로 확인**합니다 (원래 이름으로 되돌립니다)
4. 안 되면 사유와 함께 흔한 원인·조치를 안내합니다

확인이 끝나면 `report\move_ready.txt` 가 남습니다. 수집 데이터와 분석 결과는 지우지 않습니다.

정상적으로 끝나면 **정리 창은 키를 누르지 않아도 몇 초 뒤 스스로 닫힙니다**(대시보드·팀 서버도
함께 닫힙니다). 화면을 더 보고 싶으면 그 사이에 아무 키나 누르면 자동 닫힘이 멈춥니다.
**실패했을 때는 사유를 읽어야 하므로 닫히지 않고 기다립니다.**

### 옮기는 크기가 신경 쓰일 때

**[PC 이동 준비]가 알아서 줄이므로 따로 하실 일은 없습니다.** 폴더 용량의 대부분은
`data\copilot_profile`(Copilot 로그인용 Edge 프로필)인데, 이동 준비가 끝나기 직전에
옮길 필요가 없는 것을 지우고 줄어든 크기를 알려 줍니다(실측 529.2MB → 11.7MB).

그 안의 로그인 정보는 Windows DPAPI 로 **지금 이 PC·이 계정에 묶여** 있고 그 열쇠는 LoadMonitor
폴더 바깥(`%APPDATA%\Microsoft\Protect\`)에 있습니다. 그래서 폴더를 통째로 옮겨도 로그인은
살아나지 않습니다 — 어차피 새 PC 에서 한 번 로그인해야 합니다. **이 PC 의 로그인은 정리 뒤에도
그대로 남습니다**(쿠키와 토큰은 지우지 않습니다).

명령으로 옮기고 싶으시면 아래처럼 프로필을 빼도 됩니다(선택).

```
robocopy "D:\LoadMonitor24" "E:\LoadMonitor24" /E /XD copilot_profile __pycache__ .ruff_cache /R:1 /W:1 /MT:16
```

- `/MIR` 은 쓰지 마세요 — 대상 폴더에 있던 다른 내용을 지웁니다.
- 원본 폴더는 **지우지 마세요.** 새 PC 가 잘 도는 것을 확인한 뒤에 정리하시면 됩니다.
- 새 PC 에서는 `LoadMonitor30v1-UI.bat` → **[AI 연결 진단]** → 열린 전용 Edge 창에서 회사 계정 로그인
  1회 → **[AI 연결 진단]** 을 다시 눌러 성공을 확인한 뒤 분석을 실행하세요.
  (폴더가 없으면 도구가 알아서 새로 만듭니다.)
- 사내망에서 python.org 에 닿지 않는다면 `python\` 폴더는 **반드시 함께 가져가세요**
  (`tools\Get-EmbeddedPython.ps1` 은 인터넷이 필요합니다).

옮긴 PC 에서 `LoadMonitor30v1-UI.bat` 을 실행하면:

- 지난 PC 의 수집 데이터는 `data\추가PC\<이름>\` 으로 자동 보관되고
  ([로컬PC 자료수집]으로 모은 자료도 여기에 보관됩니다 — 폴더 이름 `추가PC`는 예전 그대로입니다)
- 분석은 **두 PC 를 합쳐** 계산합니다
- `report\upload_pending\` 의 업로드 대기 묶음도 함께 따라갑니다

> 폴더 안에서 정리 스크립트를 직접 실행하지 마세요 — 그 스크립트 자신이 폴더를 잡아 확인이 실패합니다.
> bat 과 버튼은 `%TEMP%` 로 복사해 실행하므로 그런 일이 없습니다.

## 6. Outlook 메일·일정 — 설정 없음

**클래식 Outlook을 켜둔 상태**에서 [분석 실행]만 하면 됩니다.
(신형 "새 Outlook"은 COM 미지원 — 우측 상단 토글로 클래식 전환)

COM 이 안 되는 PC(새 Outlook 전용·2016 시작 마법사·COM 미등록)는 자동으로 **Windows Search 색인 →
Outlook 웹 읽기(`mailViaWeb`) → Copilot 메일·일정 왕복**(`mailViaCopilot`) 순으로 대체합니다(메일이 비었을 때만).
Outlook 웹 읽기는 Copilot 과 같은 전용 Edge 창에서 **회사 계정을 한 번 선택/로그인**해 두면 동작합니다 —
진행 로그나 메일·일정 힌트에 "로그인 필요"가 보이면 그 창의 Outlook 탭에서 로그인한 뒤 대시보드 **[Outlook 웹 읽기]**를 누르세요.
무엇이 막혔는지는 대시보드 **[수집 진단]** 버튼(또는 `LoadMonitor30v1-수집진단.bat`)으로 확인하세요 —
`report\collect_diag.txt` 에 [판정]이 적힙니다(채팅·메일 내용은 마스킹). [판정]대로 **그 PC 안에서** 조치하면
되고 파일을 밖으로 보낼 필요는 없습니다.

### 받은·보낸 편지함 밖의 메일 폴더도 읽습니다 (LM28)

Outlook 웹 경로가 내 사서함의 다른 메일 폴더도 읽습니다. 규칙으로 옮긴 메일과 내가 만든 폴더의 메일도 근거로 잡힙니다.
따로 설정할 것은 없습니다(`owaExtraFolders` 기본 true). 클래식 Outlook(COM) 수집은 원래 모든 폴더를 읽고 있어 바뀐 것이 없습니다.

- **읽는 폴더** — 내가 만든 폴더, 이름을 바꾼 폴더, 받은 편지함·보낸 편지함의 하위 폴더, 보관 폴더입니다.
- **읽지 않는 폴더** — 지운 편지함·정크 메일·임시 보관함·보낼 편지함·대화 기록·RSS·동기화 문제·메모·검색 폴더·예약됨과
  그 하위 폴더입니다. 즐겨찾기·그룹·공유 사서함·온라인 보관 사서함도 읽지 않습니다.
- **받은 메일과 보낸 메일** — 보낸 편지함 아래 폴더의 메일은 보낸 메일로, 그 밖의 폴더는 받은 메일로 셉니다.
  내가 보낸 메일을 내 폴더로 옮겼다면 받은 메일로 셉니다(클래식 Outlook 수집과 같은 규칙).
- **메일을 열지 않습니다** — 폴더 목록만 읽으므로 읽음 표시가 바뀌지 않습니다. 접혀 있던 폴더는 펼쳐진 채로 남을 수 있습니다.
  폴더 이름은 저장하지 않습니다.
- **끝까지 못 읽은 폴더**가 있으면 그 날은 '일부'로 남고, 다음 실행이 다시 읽습니다.
- **폴더 창이 접혀 있으면** 다른 폴더를 못 읽습니다. 전용 Edge 창의 Outlook 웹에서 왼쪽 폴더 창을 ☰ 단추로 펼쳐 두세요.
- **업데이트 뒤 첫 실행**은 Outlook 웹이 지난 날(메일·일정)을 한 번 다시 읽어 오래 걸릴 수 있습니다. 진행 로그에
  "Outlook 웹 의 지난 '읽음' 표시를 지우고 그 날들을 다시 읽습니다"가 한 번 나옵니다.
- Copilot 메일 확인도 같은 범위(지운 편지함·정크 메일·임시 보관함 제외)를 묻습니다. 이미 답을 받은 날은 다시 묻지 않습니다.

설정: `owaExtraFolders`(기본 true) · `owaExtraFolderMax`(기본 40 — 한 번에 읽는 폴더 수, 넘는 폴더는 로그에 개수만) ·
`owaExtraFolderSkip`(읽지 않을 폴더 이름 일부, 하위 폴더도 함께 뺌 — 예: `["개인", "뉴스레터"]`).

### 회의 일정의 본문(안건)도 AI 판정의 참고로 씁니다 (LM28)

회의 제목이 '주간 회의'뿐이어도 본문의 안건이 과제를 가리키면 맞는 과제·세부업무로 분류됩니다. 본문은 걸러서 쓰고,
이 PC 밖으로는 Copilot 판정 질문에만 나갑니다. 따로 설정할 것은 없습니다(`calendar.bodyToAI` 기본 true).

- **걸러 내는 것** — Teams·Zoom·Webex 참가 안내문(참가 링크·회의 ID·암호·전화 접속), 링크, 메일 주소, 전화번호,
  참석자 목록, 전달된 메일 머리글, 맺음말을 걷어 냅니다. 그다음 사람 이름·금액 같은 개인정보를 가립니다.
  Copilot에 보내기 직전에 한 번 더 검사합니다.
- **붙이지 않는 일정** — 종일 일정, 취소·거절, 한가함, 부재중·근태, 비업무, 개인 폴더 제외어(`excludePathKeywords`)가 든 일정,
  비공개 일정, 비밀번호가 든 본문, 사적 대화로 보이는 본문입니다.
- **어디에 쓰나** — AI 판정 질문의 회의 줄 끝에 '안건'으로만 붙습니다(기본 160자, `calendar.noteMaxChars`).
  팀 서버·공유폴더로 나가는 결과와 리포트에는 들어가지 않습니다.
- **어디에 남나** — 정제한 본문은 이 PC의 `data\outlook` 안에만 남습니다(일정마다 600자까지). 화면 [데이터] 표에는 보이지 않습니다.
- **어떻게 읽나** — 클래식 Outlook(COM)은 일정 본문 앞 600자를 읽고, 비공개·기밀 일정은 읽지 않습니다.
  Outlook 웹은 지난 회의를 눌러 상세의 본문 칸만 읽고 닫습니다. 한 번 실행에 `owaCalBodyMax`(기본 60)개까지 열고,
  오늘·앞날·종일·비공개 회의와 참가 단추가 있는 회의는 열지 않습니다. 한 번 읽은 회의는 다시 열지 않습니다.
- **업데이트 뒤 첫 분석** — 안건이 붙은 회의만 AI에 한 번 더 묻습니다. 클래식 Outlook PC는 첫 수집에서 일정만 처음부터
  다시 읽습니다(메일은 그대로).
- **끄기** — `calendar.bodyToAI`를 `false`로 두면 AI 판정에 붙이지 않고, 클래식 Outlook·Outlook 웹 어느 수집도 본문을
  읽지 않습니다. Outlook 웹에서 여는 수만 줄이려면 `owaCalBodyMax`를 낮추세요(`0`이면 웹에서만 끕니다). `storeMailSubject`가
  `false`면 어느 경로도 본문을 읽지 않습니다.

### 근태·회의 판정 규칙 (2차 감사 반영 — 설정 없이 자동)

- **동료 연차 공유 초대는 부재로 세지 않음** — `[연차] 홍길동` 식 팀 공유 초대(받은 초대인데 내 상태가
  부재중이 아님)·취소된 초대·거절·미응답 초대는 내 근태가 아닙니다. 내 근태는 **내가 부재중(OOF)으로
  표시한 일정**만. COM 이 아닌 폴백 경로(색인·웹·Copilot)는 '한가함' 일정만 거릅니다.
- **복합 근태 제목 인식** — `여름휴가` `연차휴가` `오후반차` `경조사` `대체휴무` 처럼 근태어가 다른 말과 붙은
  제목도 부재로 봅니다(`휴가철 안전 캠페인`·`휴무일 근무 협조`·'연차 사용 현황' 같은 안내·공지는 제외 — 놓치면
  정상 근무로 남으므로 애매하면 안 잡는 쪽). 종일이 아닌 부재중 일정은 길이와 제목(반차·오전·오후)으로
  0.5일 / 1.0일을 판정합니다.
- **종일 출장·현장·교육·워크숍은 근무** — 종일 일정이 부재중/바쁨이거나 제목에 `출장 현장 외근 교육 세미나
  전시 박람회 고객사 방문 시험 workshop trip site training offsite field` 가 있으면 그날을 **표준일 8h**
  (반차면 4h) 하한으로 인정하고 부재 추정에서 뺍니다(`mm.offsiteAsWork`·`offsiteKeywords`). 예전엔 0h,
  PC 까지 꺼져 있으면 '부재 추정' 이었습니다(현장 주 2일 −36pt). 다일 시간제 일정은 날짜별로 잘라 각 날 8h 상한.
- **회의가 아닌 약속은 회의 시간이 아님** — 참석자 없는 개인 약속(재택근무 블록·'치과')은 회의 구간·PC 하한
  게이트에 들어가지 않습니다(출장 제목이면 위 규칙으로만 인정). 회의 제목에도 §2 의 `excludePathKeywords`
  가 걸립니다('병원 진료(개인)' 8h 방지).
- **미응답 초대** — `tentativeMeetings: "count"`(기본) 에서는 미정·미응답도 계상해 COM PC 와 폴백 PC 의
  값이 같습니다. 초대에 응답하지 않는 습관이면 그대로 두세요(§9 표).
- **폴백 경로의 한계와 보완** — Windows Search 색인은 반복 회의를 전개하지 못하므로(마스터 1건)
  `mail_source.json` 에 `calendar_complete:false` 를 남기고 웹 경로(주 보기)로 일정만 다시 시도합니다.
  웹 경로는 '6월 1일 ~ 6월 5일' 식 다일 일정을 시작~끝으로 읽고(예전엔 첫날 하루), 발신함 판정은
  폴더 이름 완전 일치라 'presentation'·'Sent from my iPhone' 수신 메일이 발신으로 둔갑하지 않습니다.
- **공휴일** — 설·추석·대체공휴일·선거일은 연도별 표(`core\extract.py` KR_HOLIDAYS, 2025~2027)가 내장돼
  `holidays` 를 비워 둬도 됩니다. 내장 표에 없는 연도·임시 공휴일만 적고, 해가 바뀌면 정부 공고로 표를
  갱신하세요. 추정 부재·공휴일은 투입 MM 의 분모(평일수)에서도 빠집니다.

### 팀즈 시각 형식이 특수한 PC (`teamsTimeRegex`)
팀즈 창 읽기는 이 PC 의 Windows 지역 설정(오전/오후 표기·시각 구분자·날짜 순서·월 이름)에서 형식을 자동
구성하고, 한 줄도 못 잡으면 일반 형식(`숫자:숫자` / `숫자.숫자`)으로 다시 시도합니다. 그래도 0건이면
[수집 진단]의 "불일치 예"(마스킹된 줄)를 보고 `config.json` 의 `teamsTimeRegex` 에 .NET 정규식을 적으세요.
그룹 순서는 `1=앞 오전/오후 표기, 2=시, 3=분, 4=뒤 표기` 이며 빈 그룹도 됩니다. 예) `14h10` 표기:
`()?\b(\d{1,2})h(\d{2})\b()?`

## 7. noticeSenders — 공지·알림 메일 제외

정부24·인화원·윤리사무국·innoHR 같은 정보성 발신은 업무도, 연결성도 아닙니다.
발신자 이름에 이 키워드가 있으면 **완전 제외**됩니다(신호 출처 카드의 '제외'에 집계):

```json
"noticeSenders": ["정부24", "인화원", "윤리사무국", "innoHR", "no-reply", "뉴스레터", "회사알림계정추가"]
```

명단에 없어도 **5통 이상 받았는데 내가 한 번도 회신한 적 없는 발신자**는
자동으로 알림성으로 판정해 0.2배로 감쇠합니다(출처에 '메일(수신전용)'으로 표시).
리뷰에서 이상한 발신자가 보이면 그 이름을 명단에 추가하면 즉시 사라집니다.

매칭은 발신자 표시 이름을 `/`·`|`·괄호·공백으로 **조각낸 뒤** 비교합니다 — `시스템` `공지` `알림` `설문`
`보안` `광고` `마케팅` `viva` 같은 일반 명사는 조각 전체가 같을 때만, 나머지(`no-reply`·`정부24`)는 조각
시작 일치. 그래서 `홍길동/책임/개발시스템팀` 이나 `공지영` 은 공지가 아니고, **내가 회신한 적 있는
발신자는 무조건 공지가 아닙니다**. 기본 목록에서 `system` 은 뺐습니다(파트명 System/OE/ME/EE 와 충돌).
`nonWorkKeywords` 도 `취소:`·`Canceled:` 류는 접두 일치, 근태어는 위 §6 토큰 규칙, `미리 알림` 은
정확 일치라 '연차 사용 현황 안내' 회의나 파일 이름이 지워지지 않습니다.

### Copilot 대화 목록 정리 — LM30v1이 연 채팅만 지웁니다 (LM28)

[분석 실행]이 끝나면 Copilot 대화 목록에 LM30v1이 연 채팅이 남지 않습니다. 판정·월별 코멘트·재시도는 지금도 새 채팅을
열지만, LM30v1은 한 채팅을 다 쓰면 다음 새 채팅을 열기 직전에 그 채팅을 대화 목록에서 지웁니다. 마지막 채팅은 작업이 끝나
전용 Edge를 닫기 전에 지우고, [AI 연결 진단]의 시험 채팅은 진단이 끝나면 바로 지웁니다.

**여는 채팅 수도 줄였습니다(2026-10-17).** Copilot에 메일·일정·팀즈를 묻는 단계는 기간 조각마다 새 채팅을 열지 않고 한 채팅에서
이어 묻습니다(`chatTurns`번마다, 그리고 답이 비정상인 조각 다음에만 새 채팅). 이어 묻는 사이에 전용 Edge 화면이 다른 대화로 바뀌면
그 대화에는 보내지 않고 새 채팅을 엽니다. 월별 리뷰 코멘트는 다른 달 내용이 섞이지 않도록 달마다 새 채팅을 씁니다.

**지우는 것** — LM30v1이 전용 Edge에서 새로 열고 프롬프트를 보낸 채팅뿐입니다. 지우기 전에 아래를 모두 확인하고, 하나라도
맞지 않으면 아무것도 누르지 않고 남깁니다.

- 지금 화면의 대화에 LM30v1이 마지막으로 보낸 줄이 있는지(프롬프트 원문은 저장하지 않고 해시로만 비교합니다)
- 화면 주소의 대화가 LM30v1이 쓰던 대화와 같은지
- 왼쪽 대화 목록에서 지금 대화의 항목이 하나로 정해지는지
- 그 항목의 제목이 LM30v1이 보낸 첫 질문의 앞부분과 같은지(2026-10-17 추가 — 제목 글은 저장하지 않고 해시로만 비교합니다)
- 그 항목의 '…(추가 작업)' 메뉴에 글자가 정확히 '삭제'인 항목이 있는지, 확인 창의 단추가 정확히 '삭제'인지

**목록이 접힌 창** — 전용 Edge 창이 좁아(화면 배율 125~150%) 대화 목록이 접혀 있으면, 지우기 전에 목록을 펼치거나 잠시 넓은 화면으로
바꿔 항목을 찾고 끝나면 되돌립니다. 무엇을 지울지는 위 확인으로만 정합니다.

**사람이 쓰던 채팅에는 질문도 넣지 않습니다** — 이어 묻기 직전에 화면이 LM30v1 채팅인지(보낸 줄·대화 주소) 확인하지 못하면 새 채팅을
엽니다. 새 채팅이 열린 것을 확인하지 못하면 보내지 않고, 그 묶음은 규칙으로 판정합니다. 분석이 도는 동안 전용 Edge의 Copilot 창에서
다른 대화를 눌러도 그 대화에는 아무것도 들어가지 않습니다.

**지우지 않는 것** — 사람이 직접 연 대화, LM30v1이 열지 않은 대화(그 대화에 LM30v1이 이어 보냈어도), 개인 Edge·LM24·LM28·LM29·LM30의 Edge는
건드리지 않습니다. 지운 뒤에도 그 채팅이 화면에 남으면 다른 대화를 지웠을 수 있다고 보고 그 뒤로는 지우지 않습니다(새 판에서
풀립니다).

**끄는 법** — `config\config.json`의 `copilotAuto.deleteChats`를 `false`로 바꿉니다. 예전처럼 채팅이 목록에 남습니다.

**사진으로 보낼 것** — 진행 로그의 `── Copilot 채팅 정리` 아래 줄(만든 n · 지운 m · 남긴 k와 남긴 까닭), 판정·정제·
워크플로우 단계 끝의 `[copilot] 채팅 정리:` 줄, [AI 연결 진단] 알림 창의 'Copilot 채팅 정리' 줄입니다. 숫자와 까닭만 있고
채팅 제목·내용은 없습니다. 남긴 수가 0이 아니거나 '삭제 멈춤'이 보이면 그 줄을 찍어 보내 주세요.

### Copilot 이 「요청이 너무 많다」고 할 때 (LM28)

**이제 오래 멈추지 않습니다.** Copilot 이 "현재 요청이 너무 많아 일시적으로 응답할 수 없습니다. 나중에 다시 시도하세요."처럼
사용량 제한을 알리면, LM30v1은 2분 한 번 쉬고 같은 묶음을 한 번만 다시 보냅니다. 그래도 막히면 이번 실행의 AI 단계(AI 판정·월별
코멘트·AI 정제·Agentic 니즈 발굴·워크플로우)를 멈추고, 여기까지의 결과는 지킨 채 보고서·팀 업로드 묶음·팀 서버 보고까지 마칩니다.
사용량 제한 때문에 Copilot 을 기다리는 시간은 한 실행에 3분 안팎입니다.

**무엇을 하면 되나** — 1~2시간 뒤 [재분석만]을 누릅니다. 이미 판정한 신호는 다시 묻지 않고 남은 것만 이어서 합니다. 멈춘 지
5분 안에 다시 누르면 첫 AI 단계가 멈춘 때부터 5분이 될 때까지만 한 번 쉬고 한 번만 보내 봅니다(이 쉬는 시간도 새 실행의
5분 합계에 듭니다) — 그래도 막히면 그 실행도 바로 멈춥니다.

**쉬는 시간 합계** — 한 번 분석에서 Copilot 때문에 쉬는 시간은 모든 단계를 합쳐 5분을 넘지 않습니다. 한 번에 쉬는 시간도
2분 이하입니다 — 답이 오지 않거나 오류 문구가 오는 일시 오류는 1분·2분·2분 쉬고 다시 보내고, 사용량 제한은 2분 한 번 쉽니다.
합계는 `copilotAuto.runWaitMaxSec`(기본 300초, 0이면 쉬지 않음)로 정합니다. 다 쓰면 그 단계의 남은 묶음은 보내지 않고 여기까지의
결과를 지킵니다. 그때 진행 로그에는 '이번 실행에서 Copilot 을 기다리며 쉬는 시간(모두 5분 — copilotAuto.runWaitMaxSec)을 다
썼습니다' 줄이 한 번 남습니다.

**예전에는** — 2·5·10분 간격으로 세 번 쉬고 다시 보냈고, 다음 단계마다 10분을 더 쉬고 한 번씩 다시 보냈습니다. 그동안 보낸 요청이
제한을 더 늘려 한 실행이 한 시간 넘게 멈춘 것처럼 보였습니다. 단계마다 따로 쉬어 한 실행이 다 합쳐 반시간 넘게 쉴 수도 있었습니다.

**어떻게 알아채나** — 제한 문구가 답 자리(말풍선)에 뜨거나 답 대신 화면 알림(토스트·배너)으로 뜨면 몇 초 안에 알아채고, 답을 끝까지
기다리거나 새 채팅을 열어 다시 보내지 않습니다. 정상 답의 앞머리에 비슷한 낱말이 잠깐 보이는 것은 몇 초 지켜본 뒤에 판단하므로
오인하지 않습니다. JSON 이 섞인 답과 긴 글은 제한 문구로 보지 않습니다. 보내기 전부터 떠 있던 알림도 근거로 쓰지 않습니다.

**진행 로그에 남는 것** — 멈춘 단계 아래에 다음 줄이 한 번 나옵니다.

> [!] Copilot 사용량 제한(요청이 너무 많음) — 이번 실행의 AI 단계를 멈췄습니다. 여기까지의 결과는 지켰고, 1~2시간 뒤 [재분석만]을 누르면 남은 것만 이어서 합니다.

실행 기록의 그 단계에도 같은 문구가 남고, 멈춘 뒤에 돈 단계는 '건너뜀 — Copilot 사용량 제한(요청이 너무 많음)으로 …'으로
적힙니다. 실패가 아니라 Copilot 이 쉬라고 한 것입니다.

**요청 간격** — 요청이 몰리지 않게 Copilot 에 보내는 사이에 15초 간격을 둡니다(`minGapSec`). 평소에는 답을 기다리는 동안 이미 지나
있어 느려지지 않습니다. 5초 넘게 기다릴 때만 진행 로그에 '요청 간격' 줄이 남습니다.

**바꾸는 법** — `config\config.json`의 `copilotAuto.throttleWaitSec`(기본 120초, 0이면 쉬지 않고 바로 멈춤),
`copilotAuto.minGapSec`(기본 15초, 0이면 끔), `copilotAuto.runWaitMaxSec`(기본 300초, 0이면 쉬지 않음)를 고칩니다. 답이 오지 않거나
오류 문구가 오는 다른 일시 오류는 1·2·2분 쉬고 다시 보냅니다(간격은 고정이고, 합계는 `runWaitMaxSec` 안입니다). 진행 로그에
'쉬는 시간'·'AI 단계를 멈췄습니다' 줄이 보이면 그 줄을 찍어 보내 주세요.

## 8-2. 캐시 파일 — Copilot 이 채운 것, 한 줄 지우면 그 항목만 원복

Copilot 이 한 번 정한 병합·분류 결과는 파일에 누적돼 다음부터는 묻지 않습니다. 결과가 이상하면
그 파일에서 **해당 줄만 지우고** 다시 돌리면 그 항목만 다시 묻고, 파일을 통째로 지우면 전부 다시
묻습니다. 원본 결과(mm_rows·signals)는 건드리지 않으므로 지워도 잃는 것은 없습니다.

| 파일 | 어디에 | 무엇 |
|---|---|---|
| `config\detail_aliases.json` | 개인 폴더 | 세부업무 표기 병합 맵(규칙 + Copilot). 옛 `report\보완툴\detail_aliases.json` 은 첫 실행에 자동 흡수 |
| `team_aliases.json` | 팀 공유폴더(서버 PC 면 `teamdata\`) 루트 | [Copilot으로 유사 항목 정리] 결과 — 과제·세부업무의 갈라진 표기 → 대표 이름. [정리 되돌리기] 가 지우는 파일 |
| `team_series.json` | 〃 | 과제 시리즈(같은 계열 과제) 묶음 |
| `team_pjclass.json` | 〃 | 과제 분류 — 애매한 이름만 Copilot 에 1회 |
| `team_detail_groups.json` | 〃 | 세부업무 계열 통합(의미 병합) |

팀 파일은 팀 취합 화면의 [정리 되돌리기] 에서 "다른 캐시도 함께 지울까요?" 로 한 번에 지울 수 있습니다.
Copilot 에 보내는 것은 어느 파일이든 **과제·업무 이름 목록뿐**입니다(사람 이름·MM 없음).

## 8-4. 창을 닫으면 작업도 멈춥니다 — 그래도 남으면 `LoadMonitor30v1-강제종료.bat` (LM28)

대시보드 창을 닫으면 도는 작업도 함께 멈추고, 대시보드 서버와 검은 콘솔 창도 닫힙니다. 창을 닫아 끝났다고 생각했는데
뒤에서 분석이 계속 도는 일이 없게 하려는 것입니다. 끄려면 `config\config.json`의 `uiAutoExit`를 `false`로 바꿉니다.

**화면 보호기·잠금·절전에서는 끊기지 않습니다(2026-10-18)** — 화면 보호기가 돌거나 PC 가 잠겼거나 3분 넘게 키보드·마우스 입력이 없는
동안에는, 브라우저가 대시보드 창을 쉬게 해 신호가 끊겨도 창을 닫은 것으로 보지 않습니다. 그동안 창을 실제로 닫았으면 예전처럼 끝납니다.
분석이 도는 동안에는 PC 가 절전(잠자기)에 들어가지 않습니다(`keepAwakeDuringRun`, 기본 켬 — 화면 꺼짐·화면 보호기·잠금은 그대로).
그래도 절전했다 깨면 그 시간은 '신호 없음'이나 수집기 '시간 초과'로 세지 않습니다. 대시보드가 스스로 끝났다면 그 까닭이
`report\ui_exit.json`과 진행 로그의 '중단(창 닫힘)' 단계에 남습니다.

**알림 창을 띄워 둔 채 다른 일을 해도 꺼지지 않습니다(2026-10-19)** — 알림·확인·입력 창(예: 팀 서버 업로드 실패 알림)이 떠 있는
동안 브라우저는 대시보드 화면을 멈춥니다. 예전에는 그 사이 3분이 지나면 창을 닫은 것으로 보고 대시보드가 꺼져, 그 뒤 [데이터 리셋]이
'리셋 실패'로 끝났습니다. 이제 화면이 창을 열기 직전에 대시보드에 알리므로, 창이 열려 있는 동안은 4시간까지 닫은 것으로 보지 않습니다.
또 도는 작업(분석·웹 읽기·리뷰 코멘트·보고서 만들기 등)이 없으면 화면 신호가 끊겨도 30분까지 기다립니다 — 멈출 작업이 없으니 서둘러
끝낼 까닭이 없습니다. 작업이 도는 중이면 예전처럼 3분입니다. 창을 실제로 닫으면 어느 경우든 약 20초 뒤 끝납니다. 대시보드가 스스로
끝났었다면 다시 켤 때 콘솔 창과 진행 로그에 '지난번에는 대시보드가 스스로 끝났습니다 — 까닭: …' 한 줄이 한 번 남습니다.

**대시보드 창(브라우저)을 닫을 때**

- 대시보드·팀 취합 화면 탭을 모두 닫으면 약 20초 뒤 끝납니다. 콘솔 창에 `[ui] 대시보드 창이 닫혀 실행 중인 작업을 멈추고
  서버를 끝냅니다` 한 줄이 잠깐 보인 뒤 창이 닫힙니다.
- 멈추는 방법은 [중지] 버튼과 같습니다. 분석·수집 프로그램을 통째로 끝내고, 우리가 띄운 전용 Edge 를 닫습니다(Copilot 채팅

- 새로고침(F5)은 20초 안에 다시 이어지므로 끝나지 않습니다. 최소화하거나 다른 탭으로 옮겨 둔 것도 닫은 것으로 보지 않습니다.
- 브라우저가 통째로 꺼져 '닫힘' 신호가 오지 못하면, 화면 신호가 3분 넘게 끊겼을 때 끝냅니다(도는 작업이 없으면 30분). 탭이 잠들거나
  (Edge 절전 탭) 알림·확인 창이 열려 있으면 닫은 것으로 보지 않고 4시간까지 기다립니다 — 몇 시간짜리 분석이 탭이 잠들었다는 이유로,
  대시보드가 알림 창을 띄웠다는 이유로 멈추지 않습니다.
- 작업이 도는 중에 창을 닫으려 하면 브라우저가 정말 나갈지 한 번 묻습니다. 나가기를 고르면 작업도 멈춥니다.
- 팀 서버(`teamserver.py`)는 팀 전체가 쓰므로 그대로 둡니다. 끄려면 팀 취합 화면의 [팀 서버 중지]를 누릅니다.

- 창의 X 를 누르면 분석·수집 프로그램이 함께 끝나고, 남을 수 있던 전용 Edge 도 닫습니다. 윈도가 몇 초만 주기 때문에 이때는

**그래도 남은 것 같을 때 — `LoadMonitor30v1-강제종료.bat`**

- 더블클릭하면 묻지 않고 이 폴더의 LM30v1 작업을 모두 끝냅니다. 대시보드·분석·수집기(PowerShell)·전용 Edge(`data\lm30v1_edge`

## 9. MM 산정 (v8 — 투입 ÷ 가용 = 로드율)

```
1 MM      = 8h × 그 달 평일수
가용 MM   = (평일수 − 부재일수) ÷ 평일수     ← 연차·휴가는 일자에서 뺀다
투입 MM   = 실제 투입시간 ÷ (8h × 평일수)    ← 상한 없음(하루 24h 물리 한계만)
로드율(%) = 투입 ÷ 가용 × 100
```

> **LM30v1 기본은 위 식이 아니라 법정 채움입니다(`mm.basis: "legal"`).** 1MM = 그달 평일 전부 × 8시간(평일 공휴일 포함)이고,
> 투입 MM = (실제 근무 + 공휴일·유급휴가 법정 채움) ÷ 1MM, 가용 MM = 지난 평일의 비율입니다. 위 식은 `"measured"`(LM30 방식)이고,
> 아래 표의 '실제 투입시간' 규칙은 두 방식이 같이 씁니다. 자세한 것은 §9-1 '1MM 기준과 법정 채움'에 있습니다.

| 상황 | 처리 |
|---|---|
| 평일 | 흔적(회의·샘플러·신호 세션) 구간의 합집합. 능동 흔적(산출물·발신·수락 회의·샘플러)이 있으면 **PC 가동 구간**(`data\pc\pc_spans.csv` ∩ 주간 창 08~19, ≤11h)을 구간째 합친다 — 점심 1h(흔적 없는 만큼) 차감, PC 가 꺼진 시간의 수락 회의는 따로 더해진다. 절전·잠금으로 꺼진 공백 중 점심·회의로 설명되는 만큼은 근무 |
| 항상 켜 두는 PC | 절전·종료 이벤트가 없어 24h 가동으로 보이는 PC 는 '첫 능동 흔적 −30분 ~ 마지막 능동 흔적 +30분' 까지만 하한(수집기가 `[pc-on] 절전·종료 이벤트 없음` 경고 — 퇴근 때 끄거나 절전 권장). 잠금 이벤트(4800/4801)는 관리자 권한이 없으면 못 읽어 `data\pc\pc_source.json` 에 `lock_events: unauthorized` 로 남는다 |

### PC 가동 하한의 근거 (LM28)

- **왜 하한이 필요한가** — 메일 발신·파일 저장 같은 디지털 신호는 '그 시각' 한 점만 남긴다. 신호만 이으면
  "3시간 작업하고 저장 1번" 이 1시간도 안 되게 잡힌다. 그래서 그날 일했다는 **능동 증거**가 있을 때만, PC 가 실제로
  켜져 있던 주간 구간을 그날 근무의 **바닥값**으로 쓴다.
- **창이 08:00~19:00 인 이유**
  1. 법정 1일 근로 8시간(근로기준법 제50조 제2항) + 8시간 근로 시 휴게 1시간 이상(제54조 제1항) → 정규 09~18시(체류 9h).
  2. 시차출퇴근(08~10시 출근) 여유로 앞뒤 1시간.
  3. PC 가동 수집기가 08시·19시 경계로 주간·야간을 나눠 적산한다 — 같은 경계를 써야 주간·야간 숫자가 맞는다
     (LM20·LM24 와 같은 값이라 팀 비교도 이어진다).
- **열리는 조건** — 그날 능동 흔적(산출물·발신·수락 회의·창 샘플러·종일 행사·수동 기록)이 있어야 한다. 수신·참조만 있는 날은
  닫힌다(단 수동 흔적 `passiveFloorMinN`(8)통 이상이 `passiveFloorMinH`(3)시간 이상에 걸쳐 있으면 연다).
- **깎는 것** — PC 꺼짐·절전 공백, 흔적 없는 점심 12~13시, 야근일 흔적 없는 저녁 식사, 반차(표준일 × 0.5 상한), 하루 상한 11h.
  창 샘플러가 덮은 시간은 하한 대신 실측을 쓴다.
- **한계와 선택** — PC 를 08~19시 켜 두고 흔적이 하나라도 있으면 최대 10h 가 잡힐 수 있다(정규 09~18 근무자의 08~09·18~19 포함).
  정규 시간만 바닥으로 쓰려면 `mm.pcFloorWindow` 를 `[9, 18]` 로 — 퇴근 경계도 18:00 이 된다. 보고서의 '산식 설정'(cfg_used)에
  쓴 값이 남고, 개인 보고서 '산출 방식' 절에 날짜별로 어느 방식(샘플러 실측·PC 하한·흔적 창·종일 행사·수동 기록)으로 셌는지,
  하한을 연 흔적 종류와 깎은 시간이 나온다.

### 측정 방식 배지·커버리지 — 팀 비교 전에 볼 것

같은 근무라도 **PC 전원 정책·권한·샘플러 유무**에 따라 수집 환경이 달라 로드율이 66~127% 로 갈렸습니다(2차 감사
실측). 그래서 분석 결과(`mm_meta_*.json` 의 `measure`·`coverage`·`cfg_used`)와 팀 취합 페이로드에 다음이 실립니다:

| 항목 | 뜻 |
|---|---|
| `measure.method` · `sampler_days` / `pc_floor_days` / `pc_record_days` / `trace_window_days` / `offsite_days` / `manual_days` | 그 기간 각 날이 어느 방식(샘플러 실측 · PC 하한 · 흔적 창 폴백 · 종일 행사 · 수동 기록)으로 계산됐는지 일수 |
| `floor_blocked_passive_days` | 수동 흔적만 있어 하한이 닫힌 평일 수 — 크면 `teamsSelfNames`·`watchFolders` 부터 확인 |
| `pc_coverage_by_month` | 월별 PC 기록 생존 비율 — 0.4 미만인 달은 '하한 미적용' 배지 |
| `coverage.grade` | `reliable`(신뢰: PC 기록 40% 이상·샘플러·캘린더 모두 있음) / `caution`(주의: 일부 결측) / `unreliable`(측정 불충분: 전부 결측) — 이유는 `reasons`. 팀 취합에서 측정 불충분은 팀 평균·순위·과제 매트릭스에서 빼고 별도 행으로 |
| `cfg_used` | standardDayHours·usePcFloor·pcFloorNeeds·dayWindow·lunch·dinner·tentativeMeetings·holidays 수·offsiteAsWork·samplerGapBridgeMin — 팀 다수와 다르면 인별 표에 **'산식 설정 상이'** 배지 |

로드율의 분모는 `standardDayHours × 평일수` 라 **standardDayHours·holidays·lunch·dayWindow 는 팀 전원이 같은 값**이어야 합니다.
팀에서 정한 `config.default.json` 값을 그대로 쓰고 개인이 바꾸지 마세요(다르면 '산식 설정 상이' 배지가 붙습니다). 팀 통합 보고서의
인별 표에서 측정 방식 배지가 다른 사람끼리(예: 샘플러 vs 하한) 소수점 차이를 따지지 마세요 — 모드 간 계통 차는 ±5pt 안으로
맞췄지만 0 은 아닙니다.

**로드율이 낮게 나오면** 먼저 UI의 'MM 산정 근거' 카드에서 *흔적 없는 평일*·*연속공백 제외 횟수*·*PC 기록 결측
평일*·*수동 흔적만 있는 평일(하한 닫힘)* 을 보세요. 이 수가 크면 실제로 덜 일한 게 아니라 수집이 덜 된 것입니다
(클래식 Outlook을 켠 상태로 재실행, `watchFolders` 확인, 팀즈 창 읽기면 `teamsSelfNames`, git 사용자는 `[git] 실행 파일 없음`
여부, 항상 켜 두는 데스크톱은 퇴근 때 끄거나 절전). 출장·현장이 0h 면 §6 의 종일 일정 규칙과 §8-3 수동 기록을 쓰세요.


## 9-1. 근태(출퇴근) 계산 — LM30

**LM30v1은 날마다 출근·퇴근 시각을 어림하고, 출근~퇴근에서 휴게를 뺀 시간으로 투입 MM을 잽니다. 기본값 그대로 두면 됩니다.**
설정은 `config\config.json`의 `attendance` 블록 하나입니다. 블록이나 키가 없으면 아래 기본값을 쓰고(LM29의 config.json을 옮겨
와도 그대로 켜집니다), 범위 밖·글자 값은 기본값으로 바꿔 쓴 뒤 'MM 산정 근거' 카드의 설정 경고에 한 줄로 알립니다.

| 키 | 기본 | 뜻 (허용 범위) |
|---|---|---|
| `useForMM` | `true` | 출퇴근 추정 근무시간으로 투입 MM을 잽니다. `false`면 투입 MM은 LM29 방식이고, 출퇴근 카드는 참고로만 보입니다 |
| `leadMin` | 30 | PC를 켠 기록이 없을 때 첫 흔적 몇 분 전을 출근으로 볼지 (0~240) |
| `tailMin` | 30 | PC를 끈 기록이 없을 때 마지막 흔적 몇 분 뒤를 퇴근으로 볼지 (0~240) |
| `pcEdgeBeforeMin` | 120 | 첫 흔적 전 이 분 안에 PC를 켰고 그 뒤 계속 켜져 있었으면 켠 시각이 출근 (0~480) |
| `pcEdgeAfterMin` | 90 | 마지막 흔적 뒤 이 분 안에 PC를 끄거나 잠갔으면 그 시각이 퇴근 (0~480) |

함께 쓰는 기존 설정: 하루 정규 시간은 `mm.standardDayHours`(8시간 — 넘으면 연장, 반차인 날은 절반부터), 야간은 `mm.nightWindow`
(22~06시 — 정규·연장·휴일 시간과 겹쳐 셉니다), 선택 상한 `mm.dayCapHours`도 그대로 적용됩니다. 주말·공휴일 근무는 전부 휴일 근무입니다.

**PC 밖·흔적이 적은 날.** PC를 끈 뒤 휴대폰으로 보낸 메일·팀즈는 PC 밖 근무로 셉니다. 그날 PC 기록이 아예 없으면 PC 밖으로 세지 않고,
흔적이 적어 출근·퇴근을 어림할 수 없는 날은 LM29 방식 시간을 그대로 씁니다(확실성 '낮음'). 종일 출장·교육은 표준일, 시간만 적은 수동
기록은 그 시간이 바닥입니다.

**이 PC에만 두는 것.** 날짜별 출근·퇴근 추정 시각과 평소 시각은 `report\attendance_<기간>.json`과 대시보드·리포트(`리포트_<기간>.html`)에만
있습니다. 근태 기록(GERP에서 읽은 것 포함)과 그것으로 센 값(+@ 중 근태 기록과 견준 것, 근태 시간 중 PC 흔적이 없는 시간, 입실·퇴실)은
합계라도 이 PC 밖으로 보내지 않습니다. 팀 서버로는 근태 기록 없이 잰 주·달 합계 시간만 가고, 공유폴더로 복사되는 얼린 보고서·분석리포트의
출퇴근 카드·절에도 그 합계만 담깁니다(+@도 추정한 값만). 단, LM30v1 기본(`mm.basis: "legal"`)의 투입 MM과 그 달 합계(실제 근무·법정
채움)에는 근태 기록이 반영되어 팀 서버로 갑니다 — 아래 '1MM 기준과 법정 채움'. 다만 [공유폴더로 저장]은 예전처럼 얼린 보고서 원문 포함본을 복사하므로, 그 안의
'수집 데이터 열람'에는 PC를 켜고 끈 시각 같은 원자료가 예전 판과 똑같이 들어 있습니다.

### +@ — 근태 기록 밖에서 LM이 찾은 근무

**근태 기록은 확실히 일한 부분이고, +@는 그 밖에서 LM이 찾은 근무입니다. 근태 기록을 못 읽어도 +@는 추정해서 늘 보입니다.** LM30 방식
(`mm.basis: "measured"`)에서는 투입 MM이 그대로 LM이 잰 근무시간이고, 근태 기록은 참고라서 MM을 바꾸지 않습니다. LM30v1 기본
(`"legal"`)에서는 근태 출근·퇴근이 있는 날의 근무를 근태 시간 + +@로 잽니다(아래 '1MM 기준과 법정 채움').

- **근태 기록이 있는 날** — 근태의 출근~퇴근(퇴근이 출근보다 이르면 다음 날 퇴근) 밖에서 일한 시간이 +@입니다. 일찍 온 시간, 늦게
  간 시간, 퇴근 뒤 따로 떨어진 저녁 근무, PC 밖 근무(휴대폰으로 보낸 메일·팀즈)가 들어갑니다.
- **휴게는 이렇게 뺍니다** — 근태 기록이 뺀 휴게(휴게 열, 없으면 4시간마다 `breakPer4hMin`분)만큼은 근태 시간 안에서 먼저 빼고,
  더 길게 일해서 늘어난 휴게는 근태 시간 밖에서(퇴근 뒤 쪽부터) 뺍니다. 그래서 근태 시간 안의 근무와 +@를 더하면 그날 근무시간이
  됩니다. 시각을 모르는 근무(LM29 방식 값·시간만 적은 수동 기록·출장 표준일로 채운 시간)는 근태 시간 안으로 봅니다.
- **전부 +@인 날** — 근태 기록 기간 안인데 그날 근태 행이 없는 날(빈 날 포함), 종일 휴가인 날, 출근·퇴근 시각이 없는 날에 일한 시간은
  전부 +@입니다(날짜별 표에 '근태 기록 없는 근무'·'휴가인 날 근무'로 보입니다).
- **근태 기록이 없는 날** — 근태 기록 기간 밖이거나 근태 기록을 못 읽은 날은 하루 8시간(`mm.standardDayHours`) 넘은 시간과 휴일
  근무 전부(종일 휴가인 날의 근무 포함)를 +@로 추정합니다. 그중 PC 밖 시간도 함께 보여 줍니다.
- **참고로만 보여 주는 것** — 근태 시간 중 PC 흔적이 없는 시간(회의·실험처럼 자리를 비운 시간 — 근태 휴게만큼은 뺍니다)과,
  태깅(입실·퇴실)이 있으면 근태 시간 밖에 건물에 있던 시간입니다. 이 둘은 근무시간에 더하지 않습니다.
- **어디서 보나** — 대시보드 카드 맨 위 줄('이번 달 +@ X시간 — 근태 기록과 견준 것 Ah · 기록 없이 추정한 것 Bh'), 주 표의 +@ 칸,
  날짜별 표의 근태 출근·퇴근·입실·퇴실·+@·까닭 칸, 리포트 8절입니다.

### 근태 기록 CSV 넣기 (선택)

ERP 등에서 내려받은 출퇴근 기록을 `data\근태\` 폴더(없으면 만듭니다)에 CSV로 넣고 [분석 실행]을 누르면, 날마다 근태 기록과 견주어
+@(근태 기록 밖에서 LM이 찾은 근무)와 '근태 기록이 없는 근무일'을 셉니다. 폴더가 없으면 견주지 않습니다(오류 아님).

```
날짜,출근,퇴근,휴게(분),인정연장,휴가
2026-09-01,08:30,17:30,60,,
2026-09-02,09:10,20:40,60,2,
2026-09-03,,,,,연차
2026-09-04,13:00,18:00,,,오전반차
```

- 꼭 있어야 하는 열은 날짜·출근·퇴근입니다(머리말은 `날짜`/`date`, `출근`/`in`/`start`, `퇴근`/`out`/`end`). 휴게(분)·인정연장·휴가는
  있으면 씁니다 — 휴게 열이 비면 4시간마다 `breakPer4hMin`분을 뺍니다. 입실·퇴실 열(태깅 — `입실`/`gate_in`, `퇴실`/`gate_out`)이
  있으면 근태 시간 밖 체류 시간을 참고로 셉니다.
- 시각은 `08:30`·`8:30:00`·`오후 6:10`·`2026-09-01 08:30` 모두 됩니다. 퇴근이 출근보다 이르면 다음 날 퇴근으로 봅니다(`25:30`도 됩니다).
- 같은 날짜가 두 줄이면 이른 출근·늦은 퇴근으로 합칩니다. 읽지 못한 줄은 건너뛰고 개수만 알립니다.
- 날짜만 있고 출근·퇴근·휴가가 모두 빈 줄(주말·휴일·기록이 없는 날)은 읽지 못한 줄로 세지 않습니다. 그날 일한 흔적이 있으면
  '근태 기록이 없는 근무일'로 셉니다.
- 인코딩은 UTF-8(BOM 있어도 됨)이나 엑셀 '다른 이름으로 저장'의 기본(CP949) 모두 됩니다.

### GERP 근무 기록 읽기 (시험 기능 — 기본 꺼짐)

**켜 두면 회사 인사 시스템(GERP)의 근무시간 현황 화면을 읽어 위 근태 기록 칸(`data\근태\gerp.csv`)을 저절로 채웁니다. 아직
시험용이라 기본은 꺼져 있습니다.** GERP 기록은 '확실히 일한 부분'으로 보고, 그 밖에서 LM이 찾은 근무를 +@로 셉니다(위 '+@').
GERP를 읽지 못하거나 로그아웃돼 있어도 +@는 하루 8시간 넘은 시간·휴일 근무로 추정해 보입니다. 켜려면 `enabled`를 `true`로 바꾸고
`url`에 본인이 쓰는 GERP 근무시간 현황 화면 주소를 붙여 넣습니다(로그인한 브라우저의 주소 창에서 복사합니다).

```json
"attendance": {
  "gerp": { "enabled": true, "url": "https://<GERP 근무시간 현황 화면 주소>", "readGate": true, "maxGateDays": 40, "timeoutSec": 60 }
}
```

| 키 | 기본 | 뜻 (허용 범위) |
|---|---|---|
| `enabled` | `false` | 켜면 [분석 실행]과 카드의 [GERP 근무 기록 읽기]가 GERP를 읽습니다 |
| `url` | `""` | GERP 근무시간 현황 화면 주소(http·https). 비어 있으면 아무것도 하지 않습니다 |
| `readGate` | `true` | 태깅(입실·퇴실) 기록도 읽습니다 |
| `maxGateDays` | 40 | 한 번에 태깅을 읽는 최대 날 수 (0~400 — 0이면 읽지 않음) |
| `timeoutSec` | 60 | GERP 화면이 뜨기를 기다리는 최대 초 (10~600) |

- **로그인은 사람이 합니다.** 대시보드 '출퇴근·시간외 근무' 카드의 [GERP 열기(직접 로그인)]를 누르면 전용 Edge 창에 GERP 화면이
  열립니다. 그 창에서 직접 로그인한 뒤 [GERP 근무 기록 읽기]를 누르세요. 이 프로그램은 아이디·비밀번호를 넣거나 저장하지 않고,
  로그아웃돼 있으면 읽지 않고 넘어갑니다(알림 없이 카드에 '로그인 안 되어 있어 건너뜀'만 보입니다).
- [분석 실행]은 수집 끝에 한 번 읽습니다([로컬PC 자료수집]·[재분석만]은 읽지 않습니다). 읽은 뒤에는 [재분석만]으로 다시 분석하면
  비교에 반영됩니다.
- 지난 날만 적습니다 — 오늘·앞날은 아직 끝나지 않았기 때문입니다. 화면에 보이는 급여 기간만 읽으므로, 읽을 때마다 날짜별로 덮어쓰며
  쌓아 갑니다. 출근·퇴근은 GERP에 적힌 시각, 입실·퇴실은 태깅의 첫 입실·마지막 퇴실입니다(다음 날 새벽 퇴실은 `25:30`처럼 적습니다).
- 주소, 날짜별 기록, 그것으로 센 값(+@ 중 근태 기록과 견준 것·근태 시간 중 PC 흔적이 없는 시간·입실·퇴실)은 이 PC에만 둡니다.
  팀 서버·공유폴더·Copilot으로는 가지 않고, 팀 서버에는 예전처럼 근태 기록 없이 잰 주·달 합계 시간만 갑니다(LM30v1 기본의 투입 MM과
  그 달 합계는 근태 기록이 반영된 값입니다 — 아래 '1MM 기준과 법정 채움'). 같은 기록을 다른 CSV로 `data\근태`에 또 넣지 마세요(같은
  날이 겹쳐 셉니다).

### 1MM 기준과 법정 채움 — LM30v1 (`mm.basis` · `mm.creditInferredLeave`)

**LM30v1은 1MM을 그달 평일 × 8시간으로 두고, 공휴일·유급휴가는 법으로 채운 것으로 친 뒤 나머지를 실제 근무로 잽니다. 기본값 그대로
두면 됩니다.** 근태 기록은 확실하게 일한 부분이고, 디지털 흔적은 인사 시스템이나 사내 시스템이 잡지 못한 근무(+@)를 보탭니다. 1MM에서
시작하지 않으므로 실제 근무가 적으면 1MM보다 낮게, +@가 있으면 높게 나옵니다.

```
1 MM      = 8h × 그 달 평일(월~금) 전부           ← 평일 공휴일도 분모에 남는다
법정 채움 = 지난 평일 공휴일 8h + 유급휴가 8h(반차 4h) + 휴가 추정 8h
실제 근무 = 근태 출근·퇴근이 있는 날: 근태 시간 + 그 밖의 디지털 +@ / 그 밖의 날: LM이 잰 근무시간
투입 MM   = (실제 근무 + 법정 채움) ÷ 1 MM          ← 상한 없음
가용 MM   = 지난 평일 ÷ 그 달 평일                  ← 휴가를 빼지 않는다(채웠으므로)
로드율(%) = 투입 ÷ 가용 × 100
```

| 키 | 기본 | 뜻 |
|---|---|---|
| `mm.basis` | `"legal"` | `"legal"`: 위 법정 채움 방식입니다. `"measured"`: LM30 방식입니다(1MM = 8시간 × 공휴일을 뺀 평일 · 투입 = 잰 근무시간 · 휴가는 가용에서 뺌 — §9의 식). 키가 없으면 `"legal"`이라 LM30의 config.json을 옮겨 와도 이 방식으로 잽니다. 다른 글자는 `"legal"`로 바꿔 쓰고 설정 경고에 한 줄 남깁니다 |
| `mm.creditInferredLeave` | `true` | 근태 기록도 휴가 일정도 없고 PC·흔적도 없는 평일(부재 추정 — `mm.inferAbsence`)을 휴가로 보고 8시간을 채웁니다. `false`면 채우지 않습니다(그날은 실제 근무가 없는 평일로 남아 투입이 그만큼 낮아집니다) |

- **날마다 이렇게 봅니다(지난 날만 — 오늘은 지난 시간만큼).**
  - 평일 공휴일(내장 표·`holidays`) → 8시간 채움. 그날 일했으면 그 근무도 더합니다.
  - 유급휴가 → 8시간(반차 4시간) 채움. 그날 근태 기록 행이 있으면 근태 기록의 휴가를, 없으면 Outlook 일정의 휴가를 씁니다.
  - 근태 기록 행이 없고 휴가 일정도 없는데 PC·흔적이 없는 평일(부재 추정) → '휴가 추정(기록 없음)'으로 8시간 채움(`creditInferredLeave`).
  - 근태 기록 행은 있는데 출근·퇴근·휴가가 모두 비었고 LM 흔적도 15분 이하인 평일 → 채우지 않고 '근태·흔적 모두 없음'으로 날짜를
    보여 줍니다(근태 기록을 확인할 날).
  - 그 밖의 평일은 채우지 않습니다 — 평일이라는 이유만으로는 채우지 않습니다. 주말은 일한 시간만 셉니다(+@).
- **실제 근무** — 근태 기록에 출근·퇴근이 있는 날은 근태 시간((퇴근 − 출근) − 휴게)에 근태 시간 밖에서 LM이 찾은 근무(디지털 +@ — 위
  '+@')를 더합니다. 근태 시간 안에서 LM이 덜 봤어도 근태 시간을 그대로 씁니다. 출근·퇴근이 없는 날은 LM이 잰 근무시간(출퇴근 추정 —
  `attendance.useForMM`이 `false`면 LM29 방식 시간)을 씁니다.
- **예 — 2026년 9월** — 평일 22일, 1MM = 176시간. 추석 연휴 3일 24시간 + 연차 1일·반차 1번 12시간 = 법정 채움 36시간. 나머지 17.5일을
  근태 기록대로 8시간씩 일했으면 근무 140시간 → (140 + 36) ÷ 176 = 1.00. 디지털 +@ 12시간이 더 있으면 1.07, 흔적으로 잰 근무가
  120시간뿐이면 0.89입니다.
- **어디서 보나** — 대시보드 'MM 산정 근거' 카드와 리포트 1절이 달마다 1MM 기준(평일 N일 × 8시간)·법정 채움(공휴일·유급휴가·휴가 추정
  일수)·근무(근태 기록 시간 + 디지털 +@ · 기록 없는 날 측정 시간)·투입 MM·가용 MM·로드율·'LM30 방식 MM(비교)'을 보여 줍니다. '휴가
  추정(기록 없음)'·'근태·흔적 모두 없음' 날짜는 카드와 리포트 8절에 있습니다. 얼린 보고서·분석리포트에는 달 합계만 담깁니다. 추이 선은
  LM이 잰 근무만 그립니다(법정 채움 없음).
- **올라가는 것** — `mm_meta_<기간>.json`의 달 칸(`mm_months`)에는 `capacity_h`(1MM 시간 — 평일 전부 × 8시간으로 뜻이 바뀌었습니다)·
  `workdays`(그달 평일 전부)·`covered`(지난 평일)·`legal_h`·`holiday_days`·`leave_days`·`inferred_leave_days`·`nohr_days`·`actual_h`
  (실제 근무)·`measured_h`(근태 출근·퇴근이 없는 날 잰 근무)·`mm_lm30`(LM30 방식 MM)·`basis`(`"legal"`)가 실려 팀 서버로 갑니다(합계뿐).
  달마다 근태 기록 시간과 디지털 +@의 나눔, 날짜 목록은 이 PC의 `report\attendance_<기간>.json`에만 있습니다.

```json
"mm": { "basis": "measured" }
```

위처럼 두면 다음 [분석 실행]부터 LM30 방식으로 잽니다. 휴가 추정한 날만 채우지 않으려면 `"mm": { "creditInferredLeave": false }`입니다.

### LM30 방식 끄기

`config\config.json`의 `attendance.useForMM`을 `false`로 두면 투입 MM이 LM29 방식으로 돌아갑니다. 출퇴근 카드와 리포트 절은
참고로 그대로 보입니다. 다음 [분석 실행]부터 반영됩니다.

```json
"attendance": { "useForMM": false }
```

## 팀즈·Outlook 은 앱을 먼저 씁니다 (`preferApp`)

`preferApp`(기본 `true`)이면 수집 순서가 이렇습니다.

- **팀즈**: Graph(설정했을 때) → **앱 창 읽기**(켜져 있는 대화) → 웹(전용 Edge) → Copilot
  앱 창에서 새 줄을 얻으면 **웹·Copilot 경로를 건너뜁니다** — 전용 Edge 탭이 아예 뜨지 않습니다.
  앱이 꺼져 있거나 화면에 렌더된 대화가 없으면(수집기 종료코드 4) 자동으로 웹으로 넘어갑니다.
- **Outlook**: COM(앱)이 1순위입니다. 앱이 0건을 돌려줄 때만 색인 → 웹 → Copilot 으로 내려갑니다.

앱 경로는 **화면에 렌더된 부분만** 읽습니다. 그래서 앱을 켜 두고 보고 싶은 대화를 열어 두면 그 대화가
가장 정확하게 들어오고, 오래된 대화까지 훑어야 할 때는 웹 경로가 필요합니다(LM30v1 에는 팀즈 상시 샘플러가 없습니다).

`false` 로 두면 예전 순서(웹 먼저)로 돌아갑니다.

## 상위(업무 성격)는 이렇게 정해집니다

상위는 네 가지입니다 — **개발 · 양산 · AX · 공통**.

| 상위 | 무엇인가 | 어떻게 알아보나 |
|---|---|---|
| **개발** | 선행·신제품·요소기술 개발 | 과제 이름이 **프로젝트 코드네임**인 경우가 많습니다 → `level1Codenames.개발` |
| **양산** | 양산 이관·양산 대응 | 역시 **코드네임** → `level1Codenames.양산` |
| **AX** | AI 를 활용한 자동화 과제 | ax·agentic·copilot·rpa·llm·자동화 같은 말(`level1AxKeywords`) |
| **공통** | 일반 사무 — 회계·재무·총무·실험실 관리 등 | 사무 키워드(`level1CommonKeywords`) |

더 필요하면 `config.json` 의 `level1Set` 에 이름을 적어 범주를 늘릴 수 있습니다(예: `["품질", "영업지원"]`).
옛 이름(신제품개발·기술 내재화·양산준비·일반업무·표준 특허)도 계속 받습니다 — 예전 결과 파일과 사내 엑셀
축이 그대로 읽히고, 화면에서는 새 이름으로 묶입니다('신제품개발'·'기술 내재화' → 개발, '양산준비' → 양산,
'일반업무'·'표준 특허' → 공통).

정하는 순서는 이렇습니다.

1. **AI 정제의 판정** — 근거를 보고 고른 값이 있으면 그것을 씁니다.
2. 비어 있으면 **코드네임 규칙** — `config.json` 의 `level1Codenames` 에 과제 코드네임을 넣어 두면
   그 이름이 과제명에 보이는 행의 상위가 확정됩니다. 양산·개발 과제는 코드네임으로 부르니 이 표가
   가장 정확합니다. 사내 코드네임은 배포본에 넣지 않았습니다 — 받는 분이 채워 주세요.
   ```json
   "level1Codenames": { "양산": ["ALPHA", "BRAVO"], "개발": ["DELTA", "ECHO"], "AX": [] }
   ```
3. 그다음 **AX 키워드**(`level1AxKeywords`, 비우면 기본 목록: ax·agentic·copilot·rpa·llm·자동화 …).
   '실험실 자동화' 처럼 사무와 겹치는 말은 **AX 로 봅니다**.
4. 그다음 **공통(사무) 키워드**(`level1CommonKeywords`, 비우면 기본 목록: 회계·재무·자금·세무·결산·
   예산·품의·정산·자산 실사·구매요청·비품·법인카드·총무·인사·근태·교육·안전·감사·실험실 관리·장비 관리·
   교정·표준·특허 …) → **공통**.
5. 어느 규칙에도 안 걸리면 **빈칸**으로 둡니다. 억지로 찍지 않습니다 — 화면에는 '상위 미분류' 로 보이고,
   판정이 갈린 과제는 '상위 혼재 — 재배치 필요' 로 따로 표시됩니다.

규칙은 **AI 판정을 덮지 않습니다**. 반대로 정제가 실패한 실행에서도 규칙이 상위를 채우므로,
예전처럼 상위 열이 통째로 비는 일은 없습니다.

## 메일 시간은 이렇게 계산됩니다

메일 한 통을 시간으로 환산하지 않습니다. **그 시각에 일했다는 흔적**으로만 씁니다.

- 받은 메일 1통 = 그 시각 앞뒤 약 5분, 보낸 메일 1통 = 약 20분의 작업 흔적(`mm.signalMinutes`).
  겹치는 흔적은 한 번만 셉니다 — 같은 시각에 10통이 몰려 와도 10배가 되지 않습니다.
- 보낸 메일은 **능동 흔적**이라 앞뒤 작업과 45분(`mm.sessionGapMin`) 안이면 한 세션으로 이어집니다.
  받은 메일은 그 다리를 놓지 않습니다(받아만 둔 메일로 하루가 채워지지 않게).
- 그 흔적들이 PC 가동 시간 안에 있으면 사이의 빈 시간도 근무로 채웁니다(PC 가동 하한, `mm.usePcFloor`).
  점심시간은 그 시간에 흔적이 없으면 빼고, 야근일 저녁도 같은 규칙입니다.
- **메일·Teams 만 한 날**: 예전에는 산출물·발신이 하나도 없으면 하루 최대 60분이었습니다(수신 80통·PC 9시간인 날이
  1.0h). 이제 수동 흔적이 `passiveFloorMinN`(기본 8)통 이상이고 `passiveFloorMinH`(기본 3)시간 이상에 걸쳐 있으면
  그날도 PC 가동 하한을 엽니다 — 같은 날이 9.0h 대로 계상됩니다. 참조 메일 한 통만 있는 날은 그대로 0.1h 미만입니다.
- **시각을 못 읽은 메일은 시간 계산에서 뺍니다.** Outlook 웹·Copilot 경로는 어제 이전 항목에 날짜만 보이는 경우가
  있습니다. 그 통수는 `data\outlook\mail_source.json` 의 `date_only` 와 대시보드 '수집 데이터 현황'에 적힙니다.
  많으면 **클래식 Outlook 앱을 켠 상태로 [분석 실행]** 을 한 번 돌려 주세요 — 앱 경로(COM)가 정확한 시각으로 다시 씁니다.
  시각을 추측해 넣지는 않습니다(하지 않은 일이 시간으로 잡히기 때문).
- 공지·시스템 발신자(`noticeSenders`)와 단체 발송은 업무에서 제외하고, 5통 이상 받았는데 회신이 없는 발신자는
  알림성으로 보아 가중치를 낮춥니다(시간 흔적은 5분으로 같습니다).

지금 이 PC 의 숫자는 `LoadMonitor30v1-가동시간비교.bat` 이 한 표로 보여 줍니다(수집 경로·'날짜만' 통수·하루 상한에
걸린 날·최근 분석 기준 근무시간).
