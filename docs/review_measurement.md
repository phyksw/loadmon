# LM25 수집·측정 설계 검토

검토일: 2026-09-09. 대상: `LoadMonitor25/collect/` 19개 수집기·진단·등록 파일, `core/extract.py`, `core/programs.py`, `mine.py`, 배포 기본설정. 목적은 **사람의 업무 투입을 근거와 한계가 드러나게 추정하고, 과제·업무별 자동화 검토의 입력을 만드는 것**으로 해석했다.

**판정: 수집의 폭과 중복 방지 기반은 적절하지만, 현재 투입 MM을 인간의 업무 투입량으로 확정하거나 개인·팀을 비교하는 데에는 부적합하다.** 특히 무인 솔버 실행 시간, 비업무로 제외한 원시 활동, 수집 공백의 부재 추정이 같은 총시간에 섞인다. 신호·시간·배분·신뢰도의 계약을 먼저 정리해야 한다. 기능을 줄이기보다는 이미 모으는 근거의 의미와 집계 경계를 맞추는 개선이 필요하다.

이 문서의 “확정”은 코드 동작 또는 합성 입력 결과를 뜻한다. 현장 사용자의 실제 오차 크기는 측정하지 않았다. 실제 수집, 앱 `main`, 네트워크, 개인 설정, 원본 `data/report`는 실행하거나 시험 입력으로 읽지 않았다. 계산 검증은 TEMP에 복제한 소스와 새로 만든 CSV로 수행했다. 결과는 [review_measurement_evidence.json](review_measurement_evidence.json)에 있다.

## 주요 문제 6개와 완료 기준

### M1 · P1 · 무인 솔버 실행이 인간 투입 MM에 들어간다 — 설계 불일치, 실행 확인

- 근거: `config/config.default.json:57`~`:60`에서 `simNight="span"`, 밤당 4h, 사람 흔적 이후 상한 해제, 내 PC 가동 불필요가 기본값이다. `core/extract.py:2205`~`:2220`은 모든 사람 흔적을 같은 밤에서 조회하며 해당 해석/과제에 연결하지 않는다. `:2978`~`:2989`가 인정 구간을 업무시간 합집합에 더한다.
- 합성 재현: 20:00~다음날 07:00의 해석 출력 구간만 있으면 4h가 인정된다. 같은 밤의 무관한 사람 흔적 22:00 한 건을 추가하면 11h가 된다. 실제 사람이 그 기간에 계속 일했다는 근거가 없다.
- 영향: 해석이 많은 담당자의 투입·야근·과제 MM이 기계 가동량과 함께 증가한다. AI 자동화 후보가 이미 자동으로 돌아가는 계산시간을 인간 업무량으로 포함할 수 있다.
- 완료 기준: 인간의 능동 작업·관측 없는 추정·무인 계산시간을 별도 지표로 분리한다. 동일 기계 실행에 확인되지 않은 사람 흔적을 더해도 인간 투입이 늘지 않아야 한다. 사람이 실제 제출/결과 확인/재실행한 구간만 업무에 귀속하고 그 근거 ID를 남긴다. 이 기준은 제품 목적에 맞춘 개선 제안이며 현장의 기존 야간 인정 정책을 승인 없이 바꿨다는 뜻이 아니다.

### M2 · P1 · 비업무로 버린 원시 활동이 총시간에는 남는다 — 확정 결함, 실행 확인

- 근거: 신호 제외는 `core/extract.py:1004`~`:1015`에 있지만 `_activity_spans`(`:2241`~`:2300`)에는 제외어/판정 결과 인자가 없다. `day_work_hours`가 원시 샘플러와 달력을 다시 읽어 합친다(`:2749`, `:2751`, `:2937`). `rehours_after_judge`는 버린 파일의 원시 시각을 제거하는 보정만 한다(`:3385`~`:3408`).
- 합성 재현: 업무 창 30분 + 개인 창 60분에서 `exclude=['개인']`으로 개인 창 신호가 제외되어 신호는 1건만 남지만, 총 투입은 1.5h이며 `dropped_h=0`이다. 알고 있는 실제 업무 0.5h가 3배가 된다.
- 영향: 버린 업무의 시간이 남은 업무에 가중 배분된다. 사용자의 제외 동작이 화면에서는 반영되어도 총량 의미가 틀린다. 달력/수동 기록을 AI에서만 제외한 경우 역시 원시 입력이 재유입되는 경로가 존재하며, 이 경로의 실제 수치는 추가 검증 대상이다.
- 완료 기준: 모든 시간 근거에 안정적인 ID·구간·포함/제외/미확정 상태를 둔다. 동일한 판정 상태를 신호·총시간·과제 귀속·재산정에 적용한다. 위 사례는 0.5h, 개인 창은 0h 귀속, 제외된 근거로 PC 하한이나 다른 업무의 MM이 다시 늘지 않아야 한다.

### M3 · P1 · 낮은 관측 범위가 ‘신뢰’로 판정되고 공백은 부재로 바뀐다 — 확정 동작, 정책 검증 필요

- 근거: `core/extract.py:2881`~`:2893`, `:3203`~`:3212`, `:3238`~`:3248`. PC가 하루에 켜진 시간이 조금이라도 있으면 기록일 1일이며, PC 평일 40%·샘플러 0일 아님·달력 0행 아님이면 `reliable`이다. 수집 완료 메타나 시간별 샘플 커버리지는 이 판정에 들어가지 않는다. 추정 부재일은 가용뿐 아니라 1 MM의 월 분모에서도 빠진다(`:3313`, `:3325`).
- 합성 재현: 요청 평일 5일, PC 기록 2일, 작업창 샘플 총 1분, 달력 1행이면 `reliable`이 된다. 나머지 3일은 부재 추정이다. 동일 투입 6.83h를 유지한 채 부재 추정을 켜면 가용 0.263→0.125 MM, 투입 0.045→0.053 MM, 로드율 17.1→42.4%가 된다. 이 예제는 실제 부재가 아니라 합성 수집 공백이다.
- 영향: 자료 누락을 직원의 부재/휴일로 해석해 로드율을 높이며, 사람마다 1 MM 분모까지 달라진다. 현장직·샘플러 중단·오래된 로그에 대한 비교가 특히 민감하다.
- 완료 기준: `관측 없음`, `수집 실패`, `확정 부재`를 분리한다. 신뢰도는 각 소스의 요청기간 완료·관측 분/가용 분·추정 시간 비율에 따라 결정하며, 위 입력은 `reliable`이 되지 않아야 한다. 미확정 공백은 분모를 자동 변경하지 않고 확인 대상으로 남긴다. 확정된 조직 근무일 기준은 모든 구성원에 공통 적용한다.

### M4 · P2 · 총시간이 업무별 신호 가중치로 전부 배분된다 — 확인된 설계 가정

- 근거: `core/extract.py:940`은 가중치를 시간 아닌 관여 강도로 정의하지만, `:1466`~`:1480`은 그 비율로 총 MM 전부를 배분한다. 약한 분류를 문턱으로 제외해도 남은 행에 전체가 재분배된다(`:1461`~`:1463`). `mine.py:224`~`:225`가 이를 호출한다.
- 합성 재현: 총 1 MM에서 A/B의 가중치가 3/3이면 각 0.5 MM이다. 같은 총시간에서 A 가중치만 6이 되면 A 0.667/B 0.333 MM이다. 이 변화는 시간 추가를 관측한 결과가 아니다.
- 영향: 저장 빈도·커밋 습관·메일량·직무별 수집 가능성이 업무 비중을 바꾼다. 기능 의도 자체가 가중 배분이므로 곧바로 계산 버그로 보아서는 안 되지만, 이것을 업무별 실측 투입이라고 설명하면 목적에 맞지 않는다.
- 완료 기준: 총시간 추정과 업무별 배분 추정을 분리 표시한다. 직접 귀속 가능한 구간은 구간 근거로 배분하고 나머지는 미배분 또는 추정 범위로 남긴다. 파일 신호 복제/누락·1분/5분 샘플·동기화 복제에 대한 배분 민감도를 표시한다.

### M5 · P2 · 수동 입력이 ‘추가 업무 시간’과 ‘하루 전체 시간’을 구별하지 못한다 — 확인된 모델 한계, 실행 확인

- 근거: `Add-WorkLog.ps1:7`~`:13`에는 날짜·시간 수만 있고 시작/종료는 없다. `core/extract.py:1754`~`:1774`는 하루 합계로 합치고, `:1255`~`:1257`은 당일 여러 업무를 한 개 신호로 만든다. `:3158`~`:3164`는 `max(관측시간, 수동시간)`을 사용한다.
- 합성 재현: 오전 PC 업무 4h와 오후 현장 업무 4h가 겹치지 않는 사례를 입력했지만 결과는 4h이며 수동 증가분은 0이다. 현재 입력 모델이 두 구간을 표현할 수 없어 발생한다.
- 영향: 혼합근무자의 누락된 현장시간을 보완하려는 목적이 달성되지 않는다. 반대로 무조건 더하면 중복이 생기므로 단순 합산도 해결책이 아니다.
- 완료 기준: 수동기록을 시간대 있는 업무 구간/하루 총량 보정으로 구별한다. 과제·담당업무별 ID를 유지한다. 비중복 4+4는 8h, 완전중복 4+4는 4h, 시각 미상은 추정 범위를 제공하는 사례를 검증한다.

### M6 · P2 · 기간 밖 메일이 현재 기간의 신호 판정과 가중치를 바꾼다 — 확정 결함, 실행 확인

- 근거: `core/extract.py:1023`~`:1034`에서 전체 저장 메일로 발신 대화·발신자 수신량·회신 이력을 만든 후, `:1098`~`:1105`에서 수신전용 감쇠를 결정한다. 기간 검사는 나중의 `add`(`:1001`)에만 있다.
- 합성 재현: 분석기간의 메일 1건을 그대로 두고 기간 밖 같은 발신자의 메일 4건을 추가하니 현재 기간의 가중치가 1.0→0.2로 감소하고 라벨이 `메일(수신)`→`메일(수신전용)`으로 변했다.
- 영향: 같은 기간의 결과가 이후 수집한 다른 기간의 데이터로 바뀐다. 소스 라벨별 최소 세션 길이도 달라질 수 있어 MM과 과제배분의 재현성을 해친다.
- 완료 기준: 분석기간 안의 메일만으로 행동 기반 판정을 하거나, 조직이 선택한 명시적인 이력 창·그 버전을 결과에 기록한다. 기본 모드에서 기간 밖 신호 추가/삭제로 기존 기간의 시간·라벨·가중치가 변하지 않아야 한다.

## 유지할 설계 3개

1. **시간 구간 합집합과 다중PC 중복 방지.** 회의 09~11/10~12는 4h를 더하지 않고 3h로, 두 PC 09~12/11~14는 6h가 아닌 5h로 계산되는 것을 합성 검증했다. 원구간과 파생 일계가 함께 남는 구조도 유지한다.
2. **투입 MM과 가용 MM 분리·부분월·야근 처리.** `mm_from_hours`의 월 전체 기준 분모, 미래 가용 제외, 가용 0일 때 월별 로드율 `None`, 야근 100% 초과 허용을 보존한다. 단 M3의 추정 부재로 공통 분모를 바꾸는 정책은 별도 수정 대상이다.
3. **관측 출처와 잡음 억제, 프로그램 지표 분리.** 파일 생성 버스트/패키지/타인 저장/열람/수동 수신을 구별하고 제외 사유를 남기며, foreground와 배경 프로세스 가동을 MM과 분리해 표시하는 방향은 적절하다. M1도 이 분리 원칙에 맞춰야 한다.

## 필요한 현장 검증과 개선 순서

먼저 M1·M2·M3의 수치 의미를 바로잡고 그다음 M5·M6과 업무별 배분을 개선한다. 원시 소스 `observation_id`, 수집 방식·원본 식별자·발생시각/정밀도·기간·host, 업무/비업무/미확정 판정, 시간 구간과 산정 규칙을 연결하는 공통 입력 계약이 필요하다. 그 위에서 인간 활동·무인 가동·관측 없음·수동 보완을 구별한다.

현장 검증은 동의한 소수 사용자의 1~2주 일지와 대조한다. 문서/개발/해석/현장 직무, 단일/다중PC, Outlook COM/웹, Teams Graph/웹/창, 회의·출장·반차·로그누락·샘플러 중단을 포함해야 한다. 모든 사람의 오류를 한 평균으로 숨기지 말고 직무/수집방식별 일 투입 오차·과제별 귀속 오차·미배분 비율·수집 완료율을 보고한다. 허용 오차는 실제 사용 목적과 함께 정하고, 그 기준을 통과하기 전 팀 순위·개인 성과 판단의 입력으로 확정하지 않는다.

검토 중 제품 소스는 수정하지 않았다. 실제 Outlook·Teams·스케줄러·라이선스 연결 성공과 실제 업무시간 정확도를 주장하지 않는다. 이 문서와 합성 재현 기록은 설계 검토 산출물이며 제품 개선 완료 기록이 아니다.
